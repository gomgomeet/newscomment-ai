# GPT-5.3-Codex-Spark 활용 가이드

작성일: 2026-08-25

대상 프로젝트: newscomment-ai 질문 중심 학생 챗봇

## 1. 핵심 결론

`gpt-5.3-codex-spark`는 학생과 직접 대화할 교사형 챗봇 모델로 곧바로 채택하기보다, 이미 방향이 정해진 프로젝트에서 작은 코드 변경과 검증을 빠르게 반복하는 개발 모델로 사용하는 것이 적합하다.

OpenAI 공식 활용 안내는 Codex-Spark를 가장 빠른 실시간 코딩 반복 모델로 설명하며, 기존 앱에서 한 가지 수정, 한 번의 검증, 다음 수정으로 이어지는 짧은 작업 순환을 권장한다. 동시에 범용 모델보다 전반적인 능력은 낮으므로 광범위한 구조 변경이나 제품 판단에는 더 강한 모델을 사용하도록 안내한다.

따라서 이 프로젝트에서는 다음과 같이 역할을 분리한다.

| 역할 | 권장 모델 사용 방식 |
|---|---|
| 교육 철학, 대화 원칙, 안전 기준 설계 | 충분한 추론 능력을 갖춘 범용 모델과 교사가 공동 결정 |
| 기존 코드 분석과 좁은 범위 수정 | GPT-5.3-Codex-Spark |
| 대화 사례 테스트 추가와 실패 수정 | GPT-5.3-Codex-Spark |
| 여러 화면·서버·데이터 계약을 아우르는 구조 변경 | 더 강한 범용 또는 장기 작업용 모델 |
| 최종 교육적 타당성 판정 | 교사 블라인드 검토와 실제 평가 루브릭 |
| 학생용 운영 LLM 선정 | 별도 안전·약관·품질 평가를 거쳐 결정 |

## 2. Spark에 잘 맞는 작업

- 특정 학생 응답에서 나타나는 어색함 한 가지 수정
- 대화 정책의 한 규칙을 코드와 프롬프트에 반영
- `studentReply` 호환 처리처럼 범위가 분명한 마이그레이션
- 한 API Route의 입력 검증 추가
- 고정 격려 문구 한 곳 제거
- 대화 회귀 테스트 3~5개 추가
- 한 화면의 간격, 버튼, 상태 표시 수정
- 오류 재현, 최소 패치, 관련 테스트 실행

한 번의 요청은 대체로 다음 질문에 명확히 답할 수 있어야 한다.

1. 어떤 한 가지 현상을 바꾸는가?
2. 어느 파일이나 기능이 범위인가?
3. 무엇을 유지해야 하는가?
4. 어떤 테스트를 통과하면 끝나는가?

## 3. Spark에서 피해야 할 요청

다음처럼 여러 종류의 판단을 한 요청에 섞으면 빠른 모델의 장점이 줄고 결과가 기계적이거나 불완전해질 수 있다.

- "챗봇을 전체적으로 더 자연스럽게 고쳐줘"
- 교육 리서치, 아동 안전, 제품 정책, 프롬프트, UI, 배포를 한 번에 처리
- 코드 근거 없이 전체 아키텍처를 새로 설계
- 여러 화면에 영향을 주는 디자인 시스템 변경
- 학생 대화 모델을 평가 없이 바로 교체
- 실제 학생 데이터나 외부 서비스에 승인 없이 쓰기

범위가 넓다면 먼저 강한 모델로 문제를 작은 구현 단위로 나눈 다음 Spark에 하나씩 맡긴다.

## 4. 권장 작업 순환

~~~text
실제 문제 한 가지 관찰
  -> 재현할 학생 발화와 기대 행동 정의
  -> 관련 코드만 읽기
  -> 최소 범위 수정
  -> 테스트 또는 브라우저 검증
  -> 결과 확인
  -> 다음 한 가지 문제로 이동
~~~

이 프로젝트에서는 다음 순서로 반복한다.

1. 10회기 합성 대화 평가에서 실패 턴 하나를 고른다.
2. 실패 이유를 `과도한 질문`, `학생 말 미수용`, `목표 강요`, `근거 없는 확장`, `종료 실패` 중 하나로 분류한다.
3. Spark에 해당 실패 하나와 관련 파일 범위만 제공한다.
4. 코드 또는 프롬프트를 최소한으로 수정한다.
5. 원래 실패 사례와 인접 사례 2~4개를 다시 실행한다.
6. 통과하면 다음 실패로 이동하고, 실패하면 같은 대화에서 남은 차이만 지시한다.

## 5. 기본 요청 템플릿

~~~text
목표:
[이번 작업에서 바꾸려는 한 가지 결과]

현재 문제:
[실제 증상, 학생 발화, 현재 챗봇 응답, 재현 방법]

수정 범위:
[살펴볼 파일, 함수, 화면 또는 대화 단계]

반드시 유지:
[기존 API 형식, 데이터 구조, UI, 호환성, 안전 규칙]

완료 조건:
[관찰 가능한 성공 조건 2~5개]

검증:
[실행할 테스트, 대화 사례, 브라우저 경로와 화면 크기]

작업 방식:
관련 구현을 먼저 확인하고 필요한 최소 범위만 수정한다.
관련 검증을 직접 실행한다.
완료 후 변경 파일, 검증 결과, 남은 위험만 요약한다.
~~~

## 6. 이 프로젝트용 요청 예시

### 6.1 "잘 모르겠어요"에 대한 관계 회복

~~~text
학생이 "잘 모르겠어요"라고 답했을 때 챗봇이 곧바로 정답이나
성취기준 설명으로 넘어가는 문제 한 가지만 수정해줘.

목표:
학생의 말을 짧게 받아 주고, 기사 속 단서 하나를 함께 살펴본 다음,
대답하기 쉬운 질문 하나만 제시한다.

수정 범위:
대화 정책과 관련 테스트만 수정한다.

반드시 유지:
현재 API 응답 형식, 화면 구조, 기존 데이터 저장 방식은 유지한다.

완료 조건:
1. 학생 응답을 구체적으로 받아 준다.
2. 한 턴에 질문은 하나만 한다.
3. 정답이나 평가 표현을 먼저 제시하지 않는다.
4. 같은 격려 표현을 반복하지 않는다.

현재 구현을 먼저 확인하고 최소 범위로 수정해줘.
관련 테스트를 추가하고 실행한 뒤 결과를 알려줘.
~~~

### 6.2 성취기준을 전면에 드러내지 않기

~~~text
성취기준이 학생에게 직접 제시되는 듯한 응답만 수정해줘.

목표:
성취기준은 대화의 숨은 방향으로 사용하고, 학생 말과 기사 단서가
먼저 드러나게 한다.

수정 범위:
curriculumCompass를 사용하는 시스템 프롬프트와 의미 검증 테스트.

완료 조건:
- 학생 응답에 성취기준 문구를 그대로 반복하지 않는다.
- 학생 생각을 먼저 받아 준다.
- 학생 관심이 생산적인 확장에 해당하면 즉시 원래 목표로 끌어오지 않는다.
- 기사에서 확인할 수 있는 단서만 사용한다.

기존 응답 스키마는 변경하지 말고 관련 테스트만 실행해줘.
~~~

### 6.3 UI의 고정 격려 문구 제거

~~~text
학생 말풍선 아래에 매번 같은 격려 문장이 표시되는 문제만 수정해줘.

수정 범위:
학생 챗봇 컴포넌트와 관련 UI 테스트.

반드시 유지:
대화 데이터 흐름, 라우팅, 교사용 화면은 변경하지 않는다.

studentReply를 화면의 단일 응답 원본으로 사용하고 고정 격려 상자를
제거해줘. 개발 서버를 실행하거나 재사용해서 해당 화면을 데스크톱과
모바일에서 확인하고, 변경 파일과 브라우저 검증 결과를 요약해줘.
~~~

### 6.4 후속 수정 요청

결과가 거의 맞을 때는 새 작업을 크게 시작하지 않고 남은 차이만 지시한다.

~~~text
방금 수정은 유지해줘.
이번에는 학생이 "그냥 그런 것 같아요"라고 짧게 대답한 경우만 조정해줘.
추궁하는 느낌을 줄이고, 기사 단서 두 개 중 하나를 선택할 수 있는
짧은 질문으로 바꿔줘. 같은 테스트 범위만 다시 실행해줘.
~~~

## 7. 검증 규칙

Spark의 빠른 결과는 검증과 결합할 때 의미가 있다. 모든 수정 요청에 최소 하나의 검증을 포함한다.

| 변경 종류 | 최소 검증 |
|---|---|
| 대화 정책 | 실패 사례와 인접 사례를 포함한 자동 대화 테스트 |
| 응답 스키마 | 타입 검사, API Route 테스트, 구버전 호환 테스트 |
| 학생 UI | 실제 브라우저에서 데스크톱·모바일 화면 확인 |
| 입력 검증 | 정상·경계·거부 요청 테스트 |
| 프롬프트 | 고정 평가 세트 전후 비교와 교사 루브릭 |

한 사례가 좋아졌다는 이유만으로 전체 품질이 좋아졌다고 판단하지 않는다. 수정한 사례뿐 아니라 인접 사례에서 새 퇴행이 생기지 않았는지 확인한다.

## 8. 더 강한 모델로 전환할 시점

다음 중 하나라도 해당하면 Spark의 짧은 반복을 멈추고 더 깊은 검토 단계로 전환한다.

- 변경이 여러 서버·화면·저장 계약에 동시에 영향을 준다.
- 새로운 대화 상태나 데이터 모델을 설계해야 한다.
- 아동 안전, 개인정보, 제공자 약관 판단이 필요하다.
- 한 문제를 세 번 수정해도 같은 실패가 반복된다.
- 접근성이나 제품 정책처럼 한 화면을 넘어서는 결정이 필요하다.
- 평가 기준 자체가 불명확하거나 교사 간 판단이 크게 다르다.

전환 후에는 문제 정의와 성공 기준을 다시 세우고, 결정된 구현 항목만 Spark 작업 단위로 되돌린다.

## 9. 프로젝트 권장 운영 분담

~~~text
교사 + 강한 범용 모델
  -> 교육적 대화 원칙과 성공 기준 결정

GPT-5.3-Codex-Spark
  -> 한 규칙 구현
  -> 관련 테스트 추가
  -> 실제 화면 또는 실행 결과 검증

교사 블라인드 검토
  -> 학생 말 수용, 질문 자연스러움, 자율성, 근거성 평가

고정 회귀평가
  -> 이전 10회기와 비교

승인된 변경만 통합
~~~

모델 이름보다 중요한 것은 명확한 범위, 실제 실패 사례, 유지 조건, 완료 기준, 검증 근거다. Spark는 이 다섯 가지가 주어졌을 때 빠른 개발 동료로 가장 유용하다.
