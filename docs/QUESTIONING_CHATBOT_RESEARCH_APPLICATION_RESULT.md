# 질문 챗봇 리서치 적용 결과

작성일: 2026-08-25

대상 브랜치: `codex/questioning-chatbot-closeout`

## 1. 작업의 전문적 명칭

이번 과정은 **시나리오 기반 합성 학습자 다중 턴 형성평가**라고 부르는 것이 가장 정확하다. 개발 관점에서는 다음 네 과정을 묶은 프리파일럿이다.

- 연구 기반 대화정책 설계
- 합성 학습자 시뮬레이션
- 다중 턴 회귀평가
- 교실 적용 전 안전·사용성 검증

실제 학생 대상 효과 연구는 아니다. 교사 검토와 학교·기관 승인 이전에 어색한 대화, 질문 소유권 침해, 자료 밖 단정, 종료 실패를 찾는 사전 품질 점검이다.

## 2. 리서치에서 코드로 옮긴 핵심

### 성취기준은 보이지 않는 나침반

성취기준 원문을 매 턴 학생에게 되풀이하거나 정답처럼 수렴시키지 않는다. `curriculumCompass`로 변환해 다음 세 항목만 내부 정책에 제공한다.

- 대화가 길게 이어질 때 돌아올 수 있는 핵심 개념
- 학생 생각을 자료와 연결할 수 있는 관찰 가능한 행동
- 이번 턴에는 성취기준을 밀어붙이지 않아도 되는 거리 판단

학생의 흥미로운 곁가지는 허용한다. 다만 자료와 무관해지거나 근거 없는 단정으로 흐를 때만 가볍게 자료로 돌아온다.

### 한 턴에 한 가지 교수 동작

서버는 모델 호출 전에 `primaryMove`를 하나 고른다. 가능한 동작은 설명, 반영, 근거 연결, 관점 확장, 낮은 부담의 단서, 불확실성 표시, 관계 회복, 안전 전환, 종료다.

한 응답에 칭찬, 설명, 평가, 질문을 모두 넣지 않는다. 학생이 답을 기다리면 먼저 답하고, 막혔으면 작은 단서를 주며, 대화를 마치려 하면 질문 없이 자연스럽게 끝낸다.

### 조건부 한 질문

직접 후속 질문 전면 금지를 제거했다. 질문은 학생 사고에 실제 도움이 되고 학생이 계속 말할 여지가 있을 때만 최대 한 개 사용한다.

- 최근 두 번의 챗봇 응답이 모두 질문이면 이번에는 질문하지 않는다.
- 학생이 짜증이나 반복감을 표현하면 설명·사과·관계 회복을 우선한다.
- `그만`, `됐어요`, `알겠어요` 같은 종료 신호에는 질문하지 않는다.
- 학생이 답을 요구한 경우 먼저 자료에 근거해 답한다.

### 학생이 보는 응답은 하나

학생 화면은 `studentReply` 한 말풍선만 렌더링한다. 기존의 고정 격려 상자와 별도 후속 질문 영역을 제거했다. 자연스러운 격려가 필요하면 완성된 응답 안에 포함된다.

## 3. 구현 구조

### 대화 계약 V2

내부 `ChatResult`에 다음 필드를 추가했다.

```text
schemaVersion: 2
studentReply
expectsStudentReply
isClosing
primaryMove
engagementState
curriculumRelation
supportLevel
sourceStatus
sourceCue
promptVersion
provider
```

기존 `answer`, `followUpQuestion`은 저장 데이터 호환용 별칭으로만 남겼다. 학생 API는 내부 분석을 제거한 최소 응답만 반환한다.

```text
schemaVersion
studentReply
expectsStudentReply
isClosing
localFallback
noticeCode (선택)
```

### 서버 대화정책

`lib/questioning-dialogue-policy.ts`가 최근 대화와 현재 발화를 보고 참여 상태, 성취기준과의 거리, 허용 질문 수, 지원 수준, 종료 여부를 먼저 결정한다. 모델은 이 범위 안에서 자연스러운 문장을 만드는 역할을 맡는다.

### 로컬 학생 경로와 외부 제공자 차단

학생용 기본 경로는 자료 범위 안에서 작동하는 로컬 응답이다. 학생 브라우저는 교사 Gemini 키를 읽거나 API 요청에 포함하지 않는다.

외부 제공자는 다음 두 서버 환경변수가 모두 명시된 경우에만 후보가 된다.

```text
QUESTIONING_STUDENT_LLM_ENABLED=true
QUESTIONING_STUDENT_PROVIDER=approved_gemini
```

이 값은 기술적 스위치일 뿐 학교·기관 승인이나 제공자 약관 검토를 대신하지 않는다. 기본값은 `false`와 `local`이다.

### 수업 설정 최소 공개

수업 코드 조회 API는 학생에게 필요한 제목, 자료, 요약, 핵심 개념, 학생용 동작 설정만 보낸다. 성취기준 원문, 루브릭, 교사 메모, 제작 PRD, API 키는 학생 브라우저에 보내지 않는다.

### 기록 분리

학생에게는 `studentReply`만 보이지만 Notion 교사용 기록에는 대화 정책 상태와 자료 근거 상태를 함께 남길 수 있다. 고정 격려 문장은 별도 기록하지 않는다.

## 5. 10회기 다중 턴 평가

### 구성

- 가상 신문기사: 6개
- 합성 학습자 회기: 10개
- 회기당 학생 발화: 4개
- 전체 학생 발화와 챗봇 응답: 각 40개
- 성취기준 조합: 제목·주제 추론, 자료 근거, 인과 관계, 관점·공감, 해결 방안, 성찰

학생 유형에는 짧게 답하는 학생, 성급히 단정하는 학생, 숫자 관계를 묻는 학생, 반복 질문에 짜증을 내는 학생, 대화를 마치려는 학생을 포함했다.

### 자동 검사

`npm run eval:questioning`은 실제 로컬 API에 40턴을 순서대로 보내 다음을 검사한다.

- 모든 응답이 V2이고 `studentReply`가 비어 있지 않음
- 한 응답의 물음표가 최대 1개
- 학생 응답에 내부 상태·루브릭·교사 메모가 노출되지 않음
- 종료 응답이 학생 답을 요구하지 않음
- 관계 회복과 종료 예상 턴에서 질문하지 않음
- 같은 문장을 연속으로 반복하지 않음

최종 결과는 **10회기, 40턴, 실패 0건**이다. 실행 상세 JSON은 로컬 검토 산출물이므로 Git에서 제외하고, 재현 가능한 fixture와 스크립트만 저장한다.

### 발견하고 수정한 문제

1. 최초 요청 제한 키가 수업 단위라 20번째 이후 합성 학생이 함께 차단됐다. 수업과 세션을 함께 사용하도록 바꿨다.
2. 소수점 `10.4kg`를 문장 끝으로 잘못 나눴다. 소수점 보호 처리를 추가했다.
3. 제목 추측 응답이 제목을 반복하거나 같은 문장을 되풀이했다. 제목 예측 의도와 최근 응답 중복을 별도로 처리했다.
4. `왜 자꾸 안 된다고 해요?` 같은 관계 손상 신호에서 다시 과제를 요구했다. 짧은 사과와 선택권 회복을 우선하도록 바꿨다.
5. 종료 발화 뒤에도 질문이 붙을 수 있었다. `isClosing=true`, `expectsStudentReply=false`를 서버 정책에서 강제했다.

## 6. 브라우저 검증

실제 개발 서버와 Chrome DevTools Protocol을 사용해 다음 흐름을 확인했다.

1. 학교·반·번호 입력
2. 학생 정보 제출
3. 채팅 시작
4. `뭐가 중요한지 모르겠어요.` 입력
5. 학생 발화와 챗봇의 단일 `studentReply` 말풍선 표시 확인

고정 격려 배너와 오류 오버레이는 없었다. 390px 모바일 폭에서 `innerWidth`와 `scrollWidth`가 모두 390px이고 화면 밖으로 넘는 요소가 없음을 확인했다.

## 8. 적용 후 달라진 학생 경험

### 이전

- 매번 비슷한 칭찬과 재읽기 안내가 붙음
- 답변 뒤 후속 질문을 전면 금지해 대화가 자주 끊김
- 또는 한 응답에서 설명과 질문이 한꺼번에 쏟아짐
- 종료와 짜증 신호를 알아차리지 못함
- 좋은 모델 응답도 UI의 고정 문구 때문에 기계적으로 보임

### 현재

- 학생 말의 뜻을 먼저 받아 주고 한 가지 도움만 제공함
- 질문이 유용한 경우에만 최대 한 개 사용함
- 잘 모르겠다는 말에는 낮은 부담의 단서를 제공함
- 반복감이나 거부감에는 관계를 회복하고 선택권을 돌려줌
- 대화를 마치려는 학생에게는 질문 없이 자연스럽게 끝냄
- 성취기준은 학생에게 보이는 체크리스트가 아니라 대화 전체의 방향으로만 작동함

## 9. 남은 한계와 다음 검증

- 이번 결과는 합성 학습자 프리파일럿이며 실제 학생 사용성이나 학습 효과를 증명하지 않는다.
- 로컬 응답은 현재 6개 평가 자료에서 세밀하게 다듬었다. 새로운 교과·자료에 대한 일반화 평가는 더 필요하다.
- 메모리 기반 요청 제한은 단일 서버의 최선형 보호다. 다중 인스턴스 운영에서는 공유 저장소 기반 제한으로 교체해야 한다.
- 학생용 외부 LLM은 기본 차단 상태다. 제공자 약관, 개인정보, 학교·기관 승인이 확인되기 전에는 활성화하지 않는다.
- 다음 단계는 교사 2명 이상의 블라인드 비교, 새 기사 홀드아웃 평가, 승인된 제한적 학생 파일럿 순서가 적절하다.

## 10. 결론

이번 적용은 프롬프트 문구만 바꾼 작업이 아니다. 응답 계약, 서버 대화정책, 학생 화면, 키 경계, 기록 구조, 회귀평가를 함께 바꿨다. 그 결과 챗봇은 성취기준을 밀어붙이는 평가기가 아니라 학생의 관심과 질문을 살리면서 필요할 때만 자료와 생각을 연결해 주는 교사형 대화 도우미에 가까워졌다.
