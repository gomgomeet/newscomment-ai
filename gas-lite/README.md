# simbot — simple bot

simbot은 simple bot의 줄임말이며, 교사가 자기 수업에 맞게 준비하는 질문 챗봇입니다.

사본 복사부터 문항별 교사 검수까지의 실습 절차는 [교사용 간단 안내](../docs/SIMBOT_TEACHER_QUICKSTART.md), 최근 운영 점검 결과는 [배포 실행 기록](../LIGHTWEIGHT_APP_DEPLOYMENT.md)을 참고한다.

이 폴더는 기존 배포본 `gas/`와 분리한 경량 Apps Script 클라이언트 패키지다. 중앙 엔진을 따로 만드는 것은 아니며, 1차시도 강사가 미리 설정한 `gas-lite` 사본으로 운영한다. 교사에게는 코드를 직접 설명하지 않고, 코드가 연결된 Google Sheet 사본을 제공한다.

## 권장 연수 진행 순서

1. 강사가 이 simbot에 수업자료와 평가 설계를 미리 입력해 학생용 챗봇을 완성한다.
2. 1차시에는 연수생이 강사의 챗봇에 학생 역할로 참여해 질문, 근거 확인, 생각 수정, 대화 종료와 평가 기록을 먼저 체험한다. 이때 연수생 개인 API는 요구하지 않는다.
3. 체험 후 강사가 설정 화면과 결과 Sheet를 열어 학생 활동이 평가 근거로 연결되는 과정을 보여준다.
4. 2차시부터 연수생이 같은 simbot의 개인 사본을 받아 자신의 API, 성취기준, 평가기준과 수업자료를 입력해 자기 챗봇을 만든다.
5. 3차시에는 학생 링크 배포, 자동 평가 초안 확인, 교사 검수와 최종 평가를 실습한다.

핵심은 `강사 완성본으로 학생 체험 → 같은 앱의 교사 구조 확인 → 각자 자기 챗봇 제작` 순서다. 체험용과 제작용의 화면·대화 엔진을 같게 유지해 초보 연수생의 설정 부담을 줄인다.

## 개인 제작 단계에서 연수생이 보는 순서

아래 절차는 강사의 완성본으로 진행하는 1차시 체험과 구조·평가 흐름 설명을 마친 뒤, 연수생이 각자 받은 사본에서 진행한다.

1. 배포용 Google Sheet 사본 만들기
2. `simbot → 1. 최초 준비`
3. `2. 교사 설정 열기`
4. 개인 API 연결
5. **1단계 수업 설정**에서 평가를 선택하고 수업 목표 또는 성취기준을 입력한다. 성취기준 코드와 내용은 한 칸에 함께 붙여 넣는다.
6. **2단계 자료 넣기**에서 본문을 입력한다. **3단계 질문·평가기준**에서 ‘필수 평가 문항 2개’와 평가 수준(3·4·5단계)을 선택한다. **AI로 필수 문항 2개 생성 → 문항 수정 → 이 2문항으로 확정 → 확정 문항의 분석 기준표 생성** 순서로 진행한다. 문항별 기준과 근거 보충 질문을 검토·수정하고 승인한다. 기존 수업의 기준별 질문계획도 계속 사용할 수 있다. 자료 탐색모드의 **3단계 대화 시작**에는 공통 시작 안내가 표시되며 별도 질문 입력은 필요 없다.
7. **4단계 저장·미리보기**에서 숫자 6자리 학생 참여코드를 입력하고 설정 저장 및 준비 상태를 확인한다.
8. 사본에서 처음 한 번만 `배포 → 새 배포 → 웹 앱`으로 학생 주소 만들기
9. 교사 설정 화면의 **전용 미리보기** 버튼을 열어 `99-999`로 실제 대화를 점검한다. 평가모드는 먼저 **글 이해하기**에서 자료에 대해 질문하고 답을 받은 뒤, **평가 시작하기**를 눌러 진행한다. 필수 2문항 평가에서는 두 문항과 근거 보충 질문을 끝까지 진행하고 답변 기록 완료를 확인한다.
10. 준비 점검이 모두 통과하면 학생용 `/exec` 주소와 참여코드를 함께 배포
11. `3. 학생 현황·평가 검수`에서 자동 초안을 확인하고 교사 최종 평가

Google Sheet를 복사하면 연결된 Apps Script도 함께 복사되지만, 학생이 접속할 웹앱 배포 주소는 사본의 스크립트 프로젝트에서 처음 한 번 새로 만들어야 한다. 이 단계는 코드 편집이 아니라 Google의 배포·권한 승인 절차다. [Google 바운드 스크립트 안내](https://developers.google.com/apps-script/guides/bound), [웹앱 배포 안내](https://developers.google.com/apps-script/guides/web)

대화 방식은 평가와 자료 탐색 사이에서 바꿀 수 있다. 자료 탐색으로 바꾸더라도 작성한 목표·성취기준·평가기준·수준 기준·평가 근거는 교사 Sheet에 보관되어 평가로 다시 바꾸면 복원된다. 탐색 중 설계는 대화 정책과 AI 입력에 적용하지 않고 학생에게 목표로 표시하지 않으며, 교사 평가 초안도 생성하지 않는다. 자료 기반 대화를 위한 공통 질문행동 관찰은 유지한다. 변경 후 **설정 저장**해야 운영본에 적용되며, 수업 개정이 바뀌므로 미리보기를 다시 확인해야 한다. 이미 저장된 학생 기록은 삭제하지 않는다.

### 글 이해 후 평가 시작 (0.11.0)

- 평가모드에 처음 입장하면 글을 읽고 낱말·사건·이유를 질문하도록 안내한다. 자료와 관련된 질문에 정상 응답을 받은 뒤 **평가 시작하기**를 선택할 수 있다. 질문 횟수만으로 평가 문항을 자동 시작하지 않는다.
- 이해 대화는 같은 대화 기록에 남기되 평가 진행과 문항별 답변·평가 초안에 포함하지 않는다. 평가 시작은 서버가 기록하며, 새로고침·재전송으로 시작 문항이나 평가 답변을 중복 저장하지 않는다.
- 평가모드와 자료 탐색모드는 모두 “글을 읽고 궁금한 것을 질문해 주세요! 제목을 보고 어떤 내용인지 생각해 볼까요?”로 새 대화를 시작한다. 자료 탐색모드에는 평가 시작 버튼이 없으며 자유롭게 자료에 대해 대화한다. 기존 대화는 저장된 기록과 진행 상태에서 이어 간다.
- 반영 순서는 **중앙 정책 v14 → GAS-lite 파일 갱신 → 웹앱 새 버전 배포 → 챗봇 연결 확인·교사 미리보기**다. 기존 사본에는 템플릿 수정이 자동으로 전달되지 않으므로 사본의 Apps Script도 갱신해야 한다.

### 필수 평가 문항 2개와 문항별 답변 분석 (0.10.0)

- 질문 생성과 기준표 생성은 별도 단계다. 교사가 수정·확정한 질문은 기준표 생성 시 AI가 바꾸지 않는다. 문항별로 핵심 답변, 원문 근거, 선택한 3·4·5단계 기준과 가상 답변 예시를 검토할 수 있다. 5단계는 A~E다.
- 자료·목표·성취기준·문항·단계 수가 바뀌면 이전 기준표는 무효가 되므로 두 문항을 다시 확정하고 기준표를 생성한다. 기준 문구와 예시는 교사가 직접 수정할 수 있다.
- 학생은 글에 대해 먼저 질문하고, 준비되면 **평가 시작하기**를 눌러 승인된 두 문항에 채팅으로 차례로 답한다. 서버는 저장된 문항별 답변 사건을 원문과 연결하고 이해 대화·일반 질문·도움 요청·건너뛰기를 평가 답변으로 혼동하지 않는다. 두 문항을 마치면 교사 Sheet의 **필수 평가 응답**에 기록하고, 이후 AI가 문항별 수준·실제 답변 인용·판단 이유·보완점을 분석한다. 브라우저를 먼저 닫은 경우 교사 대시보드에서 미시작 분석을 실행할 수 있다.
- **학생 현황·평가 검수**에서 문항별 답변과 AI 분석 초안을 확인하고 교사가 각 문항을 최종 확정한다. AI는 총점이나 최종 성적을 확정하지 않는다. 미응답을 최저 수준으로 판정하지 않는다.
- 같은 제출 번호나 동일 세션의 재전송은 유료 분석을 반복하지 않는다. 분석 실패 시 답변을 보존해 교사 검수 대기로 두며, 수신한 분석 결과의 저장 실패는 학생 재입장·교사 대시보드 조회 시 저장만 복구한다. 미리보기 결과는 실제 학생 평가에 포함하지 않는다.
- 기존 수업은 기존 질문·평가기준을 유지한다. 2문항 방식으로 전환하고 기준표까지 저장하면 새 수업 개정으로 적용되며, 기존 기록을 덮어쓰지 않는다.
- 이번 변경은 **Apps Script 소스 갱신과 기존 웹앱 배포의 새 버전 적용**이 필요하다. 중앙 대화 엔진의 기존 승인 질문계획 계약(v13)을 그대로 사용한다. `npm run test:required-assessment`와 기존 `npm run test:gas-lite`, `node evals/gas/run.mjs`로 검사한다. 자세한 흐름은 [필수 두 문항 평가](../SIMBOT_REQUIRED_ASSESSMENT.md)를 참고한다.

### 기존 단일 질문과 3~5단계 기준 만들기

- 개인 API 연결 확인 후 수업 목표 또는 성취기준 내용 중 하나 이상과 30자 이상의 자료 본문을 입력한다. 성취기준 코드는 명시적으로 입력된 코드만 분리하며 공식 원문을 추측하지 않는다.
- AI는 **학생 시작 질문 하나 → 답변의 핵심 요소 → 자료의 근거 문장 → 평가기준·선택한 수준별 기준과 가상 학생 답변 예시 → 수집할 평가 근거**를 한 묶음으로 제안한다. 수업 전에 예상 답변 유형을 설계하는 기능이며 실제 학생 답변을 채점하지 않는다. 핵심 요소의 포함·누락, 사실의 정확성, 근거 연결로 수준을 구별하고 관찰하지 않은 교사 도움 여부나 실천 행동은 추정하지 않는다. 다른 표현이나 여러 타당한 의견도 인정한다.
- 선택 가능한 수준은 **3단계: 도달·성장 중·도움 필요**, **4단계: 매우잘함·잘함·보통·노력요함**, **5단계: A·B·C·D·E**이다. A를 가장 높은 수준으로 사용하며 입력되지 않은 점수나 배점은 만들지 않는다. 선택한 단계가 생성 요청, 초안 표시, 저장, 교사 최종 판단 선택지까지 일치한다. 단계 수를 바꾸면 생성 중이거나 검토 중인 이전 초안을 무효화한다.
- 자료 본문 전체(최대 30,000자), 학년·교과와 입력된 목표를 연결한 개인 OpenAI API에 보낸다. 학생 대화·참여코드·API 키는 생성 입력에 넣지 않으며 API 사용료가 발생한다. 자료와 목표가 맞지 않거나 인용 근거가 실제 원문과 일치하지 않으면 초안을 적용하지 않는다.
- **AI 생성 → 초안 확인 → 입력란·질문계획에 적용 → 교사 검토·승인 → 설정 저장** 순서다. 생성만으로 기존 기준을 덮어쓰거나 수업을 저장하지 않는다. 비어 있는 질문계획은 평가기준·처음 질문·보충 질문·수집할 수행·본문 힌트로 자동 완성하지만 승인하지 않는다. 교사가 이미 작성한 질문계획은 덮어쓰지 않고, 새 평가기준에 맞는지 다시 확인하도록 기존 승인을 해제한다. 생성 중 또는 적용 전 입력이 바뀌면 이전 초안을 적용할 수 없다.
- 기존 3단계·4단계 수업과 과거 교사 판단은 보존된다. 단계 수를 바꾸면 각 수준 내용을 확인한다. 수동 전환 시 숨겨진 기준은 보관하며 새 AI 초안을 적용하면 해당 단계에서 사용하지 않는 기준은 비운다. 학생 자동 관찰 점수는 교사의 수행평가 최종 등급을 대신하지 않는다.
- 승인한 평가 질문은 학생이 **평가 시작하기**를 누른 뒤 제시한다. 답변의 핵심 요소, 자료 근거, 수준별 가상 답변 예시는 교사용이며 학생 화면과 중앙 학생 대화 엔진에 전송하지 않는다. 예시는 교사가 검토·수정할 수 있으며 기존 시트 끝에 선택 열 `answerExamples`로 저장한다. 수준별 기준도 학생 화면에 표시하지 않는다. 교사 검수 화면에서 해당 수업·개정·학생 접속의 평가 응답과 기준을 대조한다. 공통 대화 관찰 점수는 생성한 문항의 자동 채점 결과가 아니며 최종 수준은 교사가 정한다.
- 이 기능은 앱 0.9.0 / 중앙 엔진 정책 v10 이상에서 지원한다. 교사 Apps Script(AssessmentDraftService 포함)와 기존 웹앱 배포 버전을 갱신한다. 기존 목표 기반 평가기준 생성 서버 함수도 호환성을 위해 유지한다. 첫 평가 응답에는 정오를 단정하지 않고 응답 수집을 알리며 후속 자료 질문을 받는다.
- 중앙 정책 v11은 ‘주민’이 포함된 정상적인 수업 답변을 개인정보·대필로 오인하던 규칙을 수정한다. 주민번호·주민등록번호와 실제 대필 요청의 보호는 유지한다. 기존 사본은 중앙 배포 후 **4단계 저장·미리보기 → 연결·배포 관리 → 챗봇 연결 확인**을 누르고 전용 미리보기를 다시 실행한다. 이 수정만을 위해 Apps Script 소스나 웹앱을 재배포할 필요는 없다.
- 중앙 정책 v12는 찬반 이유를 물을 때 해당 당사자가 밝힌 요구·우려·목적을 우선 찾고, 다른 당사자의 발언과 구분한다. AI에는 일부 발췌만 보고 전체 지문에 이유가 없다고 단정하지 않도록 안내한다. 갱신 후 연결 확인과 교사 미리보기를 다시 실행한다.
- [OpenAI Structured Outputs](https://developers.openai.com/api/docs/guides/structured-outputs)에 따라 고정 JSON 형식과 필수 항목을 검증한다. 불완전한 응답은 기존 입력을 보존하며 오류로 안내한다.

4단계의 백워드 설계·운영 모드·수업자료·참여코드 점검은 현재 입력 내용을 즉시 표시한다. 아직 저장하지 않은 변경이 있으면 **변경 사항 저장 필요**로 표시하고 미리보기·학생 링크 복사를 막는다. **준비 상태 새로고침**은 API·배포 확인 상태를 갱신할 뿐 설정을 저장하지 않으며, 입력 중인 내용과 스위치 선택은 유지한다. 저장 성공 후에만 저장 전 안내가 사라진다.

이 기능은 중앙 엔진 정책 `questioning-dialogue-v2-lite-adapter-v13` 이상과 함께 사용한다. 이전 엔진에 화면만 먼저 적용하면 빈 평가 설계 요청이 거절될 수 있으므로, 중앙 엔진을 먼저 반영한 뒤 교사 시트의 Apps Script를 갱신한다. 기존 배포본은 엔진 연결 확인을 다시 실행하고, 학생용 웹앱이 있다면 동일 배포에 새 버전을 적용한다.

### 평가기준별 질문·근거 계획

3단계의 **⑤ 평가기준별 질문·근거 계획**에서 최대 5개 평가기준 카드를 작성한다. AI 질문·평가기준 초안을 적용하면 비어 있는 계획에 첫 카드가 자동으로 채워진다. 각 카드에 기준, 학생 수행 유형(설명하기/학생 스스로 질문 만들기), 처음 질문, 보충 질문, 수집할 학생 수행, 본문에서 고른 힌트 구절을 연결한다. 학생의 자료 직접 인용을 요구할지도 선택한다. 자동 초안은 항상 미승인 상태이며 교사가 최종 검토한다.

1. 질문은 한 문장 끝에 물음표 하나로 작성하고, 힌트는 3단계 수업자료에 실제 있는 구절을 넣는다.
2. **질문 진행 미리보기**에서 질문·힌트·수집할 수행을 확인한 뒤 교사 승인에 체크하고 4단계에서 저장한다. 질문이나 관련 수업자료를 바꾸면 승인이 해제된다.
3. 챗봇은 승인된 첫 질문으로 시작한다. 답변 형식/필수 자료 인용이 부족하면 지정된 보충 질문을 한 번 하고, 여전히 부족하면 교사 확인 대상으로 남긴다. 힌트와 학생의 도움 요청은 평가 답변으로 세지 않는다.
4. 교사 현황 화면에서 기준별 실제 질문·학생 답변·인용 확인·도움 사용을 검토하고 최종 평가를 직접 확정한다.

**‘응답 수집됨’은 성취기준 충족이나 점수가 아니다.** 현재 검사는 답변/질문 형식과 6자 이상 학생 인용이 본문에 있는지 확인하는 수집 보조다. 본문 인용의 적절성, 설명의 정확성, 수행 수준은 교사가 판단한다. 학생 질문을 챗봇이 대신 작성하지 않는다.

평가 설계를 끄면 계획을 보관만 하고 자료 탐색모드에서는 실행하지 않는다. 평가모드는 기준별 질문계획을 하나 이상 완성하고 교사가 승인해야 저장·미리보기·학생 배포를 진행할 수 있다. 기존의 빈 계획이나 미승인 초안은 열어 수정할 수 있지만 평가모드의 일반 대화로 조용히 대체하지 않는다. 자료 탐색모드에서는 빈 계획과 초안을 저장해 보관할 수 있다. 기존 학생 기록은 삭제하지 않으며, 새 계획은 새 수업 개정으로 구분한다.

기준별 계획은 **중앙 정책 `questioning-dialogue-v2-lite-adapter-v13`과 새 GAS-lite 파일을 함께 반영**해야 한다. 중앙 엔진을 먼저 갱신하고 시트를 갱신한 뒤 연결 확인·현재 수업 미리보기를 다시 한다. 새 계획을 지원하지 않는 구버전 엔진 응답은 오류로 막으며 일반 대화로 조용히 대체하지 않는다. 기술 계약과 검증 범위는 [질문·근거 계획 계약](../SIMBOT_ASSESSMENT_PLAN.md)에 있다.

### 한 학급 운영 기준

Apps Script 웹앱을 `배포 사용자로 실행`하면 학생 요청이 모두 교사 계정의 동시 실행 수에 포함되고, Google이 공개한 사용자당 동시 실행 상한은 30이다. 따라서 이 버전은 **동시 제출 25명 이하**를 권장하며, 30명 학급은 15명씩 두 모둠으로 나누어 약 10초 간격으로 입장과 첫 질문을 시작한다. 넘친 요청은 같은 전송 번호로 무작위 간격을 두고 다시 확인하므로 중복 과금을 만들지 않지만, 실제 학교 계정에서 사전 부하 점검을 마치기 전에는 전원 동시 제출을 안내하지 않는다. [Apps Script 할당량](https://developers.google.com/apps-script/guides/services/quotas), [웹앱 실행 주체](https://developers.google.com/apps-script/guides/web)

## 운영자가 배포본을 만들 때

별도의 중앙 서버를 만들지 않는다. 이 저장소의 기존 질문중심 챗봇(`https://newscomment-ai.vercel.app`)을 배포하면 같은 앱 안에서 아래 두 simbot 연결 경로가 함께 열린다.

- `https://newscomment-ai.vercel.app/api/lite-engine/plan`
- `https://newscomment-ai.vercel.app/api/lite-engine/finalize`

운영 순서는 다음과 같다.

1. 기능 브랜치의 Vercel Preview에서 임시 Preview plan 주소로 인증·계약 검사를 마친다.
2. 기능 브랜치를 `main`에 병합해 기존 `newscomment-ai` 프로덕션으로 배포하거나 해당 배포를 Production으로 승격한다.
3. Production의 런타임 로그와 환경변수 적용 범위를 확인해 HTTP 500의 원인을 해결하고 `/api/health`와 `/questioning-chatbot`이 정상 응답하는지 확인한다. 로컬에서는 Supabase 공개 환경변수 누락으로 같은 증상을 재현했지만, 운영 오류의 원인은 로그 확인 전까지 확정하지 않는다.
4. Production 서버 전용 환경변수 `LITE_ENGINE_ACCESS_KEY`에 32자 이상의 임의 값을 설정한다.
5. 같은 값을 로컬 환경변수 `LITE_ENGINE_ACCESS_KEY`에 넣고 저장소 루트에서 `npm run build:gas-lite-distribution`을 실행한다. 이 명령은 키가 주입된 `tmp/gas-lite-distribution/`을 만들며, 실제 키를 로그에 출력하거나 저장소에 커밋하지 않는다. 연수생이 이 값을 입력하게 하지 않는다.
6. `LITE_CENTRAL_ENGINE_URL_`은 기존 질문중심 챗봇의 Production plan 경로로 유지한다. 다른 서버 주소를 새로 만들지 않는다.
7. 인증된 GET plan이 `schemaVersion: 1`, `engineFamily: questioning-dialogue-v2`, `sharedWithWebChatbot: true`를 반환하고, 유효한 예제로 POST plan·finalize가 성공하는지 검사한다. 잘못된 키는 401, 서버 키 누락은 503이 정상이다.
8. 빈 Google Sheet에 생성된 `tmp/gas-lite-distribution/`의 `.js`·`.html`·`appsscript.json` 13개 파일을 연결하고, 교사 화면의 **챗봇 연결 확인**을 성공시킨다. README와 `DISTRIBUTION-NOTICE.txt`는 스크립트 파일로 올리지 않는다.
9. 웹앱은 실행 사용자를 `배포 사용자`, 접근 사용자를 학교 정책이 허용하는 범위에서 학생이 접속할 수 있도록 배포한다.
10. Sheet의 `1. 최초 준비`를 실행해 교사 접근 토큰과 여섯 시트(시작하기·수업 자료·학생별 현황·질문과 답변·교사 평가·필수 평가 응답)를 만든다.
11. 운영용 수업·학생 결과·개인 API 키가 남지 않은 깨끗한 템플릿을 사본 만들기 링크로 공유한다.

실제 배포 대상, 확인된 운영 상태와 계정 접근이 필요한 다음 단계는 [배포 실행 기록](../LIGHTWEIGHT_APP_DEPLOYMENT.md)에 정리한다. `gas/.clasp.json`은 기존 학생용 앱의 프로젝트다. 새 simbot 파일을 그 프로젝트로 push하지 않고, 새 빈 Sheet에 연결된 별도 Apps Script 프로젝트를 사용한다.

`LITE_ENGINE_TEST_BASE_URL`에 점검 대상 origin을 명시하고 `npm run check:lite-deployment`로 읽기 전용 접속 검사를 실행할 수 있다. 연결키 없는 검사는 인증 완료로 표시하지 않으며, 이 검사가 통과해도 실제 개인 API·학생 기록·교사 검수 확인은 별도로 필요하다.

교사 API 키는 Script Properties에 저장한다. 배포용 사본에서 개인 API 키·운영본 연결 ID·저장된 웹앱 주소·접근 토큰 등 개인 스크립트 속성이 비어 있는지 확인하고, 각 교사가 자신의 사본에서 본인의 API 키를 입력한다. `최초 준비`와 `새 수업 복제`는 기존 학생 기록을 삭제하지 않는다. 운영본과 별도로 만든 배포 사본에서 기록을 정리하고 새 수업 ID·참여코드를 사용하며 평가 승인을 해제한 뒤 공유한다.
학생 반-번호는 본인 인증값이 아니라 익명 기록 표지다. 숫자 6자리 수업 참여코드는 링크만 아는 외부인의 우발적 진입을 줄이지만 학생 개인을 인증하지는 않는다. 대화·자동평가는 브라우저 탭별 기기값으로 분리되므로 같은 번호를 다른 기기에서 입력해도 기존 대화는 노출되거나 점수가 합쳐지지 않으며, 교사 대시보드에 중복 접속으로 표시된다. 수업 중 번호 입력은 교사가 안내·확인하고, 원격·무감독 배포에는 명부별 PIN 또는 학교 인증을 후속 적용한다. 입장만으로는 Sheet에 행을 만들지 않고 첫 질문을 보낼 때 시작 질문과 첫 턴을 함께 기록한다.

`LITE_ENGINE_ACCESS_KEY`는 공개 인터넷의 무작위 호출을 줄이고 허용된 배포 패키지를 식별하는 공유 자격증명이지, 개별 교사를 인증하는 강한 비밀은 아니다. 교사 Apps Script 원본을 열 수 있는 사람은 값을 볼 수 있다고 가정한다. 유출이 의심되면 서버 키를 교체하고 새 키를 주입한 템플릿을 다시 배포하며, 이전 사본은 연결이 끊겼음을 안내한 뒤 새 사본으로 교체한다. 공통 질문 정책 변경에는 사본 재배포가 필요 없지만, 연결키 회전이나 API 계약 변경에는 사본 업데이트가 필요하다.

### 1차시 강사 운영본 당일 점검

- 새 수업으로 복제해 새 `lessonId`·개정 번호·6자리 참여코드를 사용한다.
- 강사 개인 API와 **기존 챗봇 연결 확인**을 실제로 성공시킨다.
- 교사 전용 주소에서 `99-999` 미리보기 질문을 보내고 Sheet 기록을 확인한다.
- 일반 학생 주소와 참여코드로 학생 역할 1회를 끝까지 실행한다.
- 당일 배포할 URL·참여코드가 맞고 이전 학생 결과가 현재 수업에 섞이지 않는지 확인한다.
- 25명 이하는 동시 시작, 30명은 15명씩 약 10초 간격으로 시작하도록 안내한다.

## 데이터 경계

- 기존 질문중심 챗봇의 simbot 경로로 전송: 익명 세션 키, 수업·평가 설정, 대표 개인정보 형식을 가림 처리한 학생 발화, 최근 대화
- 기존 질문중심 챗봇으로 전송하지 않음: 교사 API 키, Google Sheet ID, 교사 이메일
- 교사 Sheet에 저장: 수업자료, 학생 대화, 자동 판단 초안, 교사 최종 판단과 향상 방법
- 학생 화면에 제공하지 않음: API 키, 평가기준 원문, 수준별 루브릭, 교사 피드백

자동 가림은 완전한 개인정보 탐지기가 아니다. 이름·주소·전화번호·계정정보를 학생이 처음부터 입력하지 않도록 안내하고, 실제 배포 전 학교의 개인정보·외부 AI 사용 정책을 확인한다.

## 현재 코드에 포함된 운영 보호

- 공개 학생 주소와 분리된, 현재 수업에만 유효한 만료형 교사 미리보기 주소
- 일반 학생의 `반-번호 + 숫자 6자리 수업 참여코드` 서버 검증
- 한 학생 번호·수업당 20회(기기 변경 포함), 수업 전체 분당 90회·하루 900회 공통 엔진 요청 제한
- 개인 API 분당 60회·하루 300회 제한
- 같은 세션의 동시 요청 직렬화와 요청 ID 재사용 공격 차단
- 비정상 종료 뒤 남은 요청 잠금 자동 정리
- 유료 API 응답을 Sheet 저장 전에 단계별로 임시 기록해 저장 재시도 때 중복 과금 방지. 호출 시작 뒤 결과 유실로 과금 여부가 불명확하면 자동 재호출을 멈추고 교사 확인 안내
- 학생 브라우저 새로고침 후에도 현재 수업 입장 검사보다 같은 전송 번호를 먼저 확인하여, 수업 종료·개정 뒤 남은 Q&A·학생 현황·평가 초안을 원래 수업에 마무리
- 요청 시작 때의 수업·API·중앙 엔진 세대를 복구 기록에 고정하고, 설정이 바뀌면 과거 유료 후보를 새 엔진으로 보내지 않고 저장된 안전 답변만 사용
- 자동 평가 초안, 교사 검수, 최종 확정의 상태 분리
- 새 학생 요청의 근거 누적 시 확정 평가를 재검수 상태로 전환하고, 오래 열린 교사 카드의 저장 차단

서버의 짧은 요청 제한은 Vercel 인스턴스 메모리를 사용하는 보조 방어선이다. 교사 Apps Script의 한도를 비용 보호의 기본선으로 사용하며, 교실 밖 불특정 다수에게 공개하기 전에는 호스팅 계층 또는 공유 저장소 기반의 전체 제한을 추가한다.
