# 질문하기 수업 HTML 보드형 챗봇 PRD

## 1. 목적

교사가 성취기준을 고르고, 학생 평가 루브릭을 확인한 뒤, 수업 자료 이미지를 넣어 자료 범위 안에서만 작동하는 질문 도우미 챗봇을 준비하는 보드형 도구를 만든다.

이 챗봇은 학생이 한 질문·대답·생각을 먼저 구체적으로 받아 주고 수업 자료와 연결해 대화한다. 성취기준은 매 턴 달성시키는 체크리스트가 아니라 대화 전체의 보이지 않는 나침반으로 사용한다. 한 턴에는 설명, 반영, 근거 연결, 단서, 관점 확장, 관계 회복, 종료 중 한 가지 동작을 우선하며, 질문은 학생 사고에 실제 도움이 될 때만 최대 한 개 사용한다. 활동지 정답 전체 작성이나 수행평가 대필은 하지 않는다.

교사용 보드의 Gemini API 연결은 자료 이미지 분석과 성인 교사의 미리보기에 사용한다. 학생용 대화는 자료 범위의 로컬 응답을 기본값으로 하며 학생 브라우저는 교사 API 키를 읽거나 전송하지 않는다. 학생용 외부 모델은 제공자 약관, 개인정보, 학교·기관 승인을 확인한 뒤 서버 환경변수로 명시적으로 허용한 경우에만 사용할 수 있다. Notion DB 접근과 기록은 모델이 아니라 웹앱 서버 API가 담당한다.

구현은 두 개의 HTML 화면으로 나눈다.

- 교사용 보드: `/questioning-board`
- 학생용 질문 도우미 챗봇: `/questioning-chatbot`
- 기본 성취기준 자료: `2022 개정 교육과정 및 성취기준 분석 — 질문하기 수업·챗봇 활용`

## 2. 핵심 사용자

| 사용자 | 사용 목적 |
| --- | --- |
| 교사 | 성취기준 선택, 평가 루브릭 확인, 수업 자료 입력, 챗봇 제작 PRD 준비 |
| 학생 | 수업 자료에 대한 질문·대답·생각을 나누며 새로운 궁금증으로 대화 이어 가기 |
| 교사/실습생 | 학생 질문 유형, 대화 내용, 개선 제안을 평가·피드백 자료로 활용 |

## 3. 주요 흐름

1. 교사가 학년·교과·단원을 적고 성취기준을 선택하거나 직접 입력한다.
2. 보드는 성취기준을 핵심 성취, 내용 요소, 수행 행동, 평가 요소, 학생 산출물로 분석한다.
3. 분석 결과를 바탕으로 선택한 성취기준에 맞는 0~5점 평가 루브릭을 만든다.
4. 교사가 질문 자료 이미지를 업로드하거나 학생에게 보여 줄 전체 텍스트를 직접 입력한다.
5. AI는 이미지의 전체 텍스트를 원래 순서와 문단 구조대로 추출하고, 내부 판단용 요약·핵심 개념·질문 씨앗·오개념 가능성을 별도로 정리한다.
6. 교사용 보드는 학생용 챗봇에 들어갈 제작 PRD와 설정을 생성한다.
7. 학생이 `채팅 시작`을 누르면 챗봇이 먼저 인사하고 질문 자료에서 눈에 들어온 내용이나 궁금한 점을 묻는다.
8. 학생용 챗봇은 교사용 보드의 질문 자료 전체 텍스트를 요약하거나 생략하지 않고 보여 주며, 학생의 질문·대답·생각을 먼저 받아 주고 자료와 연결해 응답한다.
9. 챗봇은 참여 상태와 최근 대화를 보고 한 가지 교수 동작을 선택한다. 질문은 필요할 때만 최대 한 개 사용하고, 짜증·반복감에는 관계를 회복하며, 종료 신호에는 질문 없이 마친다.
10. 웹앱 서버는 학생이 본 `studentReply`와 교사용 내부 분석을 분리해 학교·반·번호를 합친 `학교_반_번호` 페이지에 누적 저장한다.

## 3-1. 최종 운영 모델

연수와 실제 수업에서 목표로 삼을 운영 모델은 다음과 같다.

1. 교사가 교사용 보드에서 성취기준, 질문 자료, 챗봇 역할, 평가 루브릭을 준비한다.
2. 교사가 `노션 준비 DB에 저장`을 누르면 웹앱 서버가 챗봇 수업 준비 DB에 수업 준비값을 기록한다.
3. 교사가 `현재 설정을 챗봇에 적용`을 누르면 학생용 챗봇이 같은 주소에서 최신 설정으로 작동한다.
4. 학생은 `/questioning-chatbot`에 접속해 학교, 반, 번호를 입력하고 질문 챗봇과 대화한다.
5. 학생 대화는 로컬 자료 기반 응답을 기본으로 한다. 승인된 외부 모델은 서버에서만 호출하며 학생 브라우저에 키나 교사용 설정을 보내지 않는다.
6. Notion API도 교사 개인 Integration과 교사 개인 Notion 템플릿 DB를 사용한다.
7. Gemini API는 Notion에 직접 접근하거나 기록하지 않는다.
8. 웹앱 서버 API가 교사별 연결 정보를 찾아 Notion API로 학생 질문과 챗봇 답변을 챗봇 수업 결과 DB의 `학교_반_번호` 페이지에 누적 저장한다.
9. 교사는 Notion 결과 DB에서 학생별 결과물을 확인하고 평가 기록과 세특용 피드백으로 정리한다.

현재 구현은 같은 브라우저의 `localStorage` 미리보기와 수업 코드 기반 서버 연결을 모두 지원한다. 교사가 준비한 성취기준·질문 자료·루브릭·PRD는 준비 DB에 남기고, 학생 질문·챗봇 답변·내부 평가 분석은 결과 DB의 `학교_반_번호` 페이지에 누적한다.

운영형의 목표 구조는 웹앱을 교사마다 복제하지 않는 것이다. 공통 Vercel 웹앱 서버 1개를 두고, 교사별 Gemini API 키와 교사별 Notion API 토큰, 자동 탐색된 준비 DB/결과 DB 연결값, 수업 코드를 Supabase에 최소 정보로 저장한다. Supabase는 학생 활동 기록 저장소가 아니라 교사별 수업 연결정보를 안전하게 찾는 작은 금고 역할만 한다. 학생 질문·챗봇 답변·평가 결과의 본문은 교사 개인 Notion 결과 DB에 저장한다.

권장 운영 규모는 연수 1회차 교사 40명 내외이다. 같은 웹앱 서버를 복제하지 않고 여러 회차에 계속 사용할 수 있지만, 안정 운영의 1차 목표는 월 400명 내외로 잡는다. 공개 서비스처럼 수백 명 이상이 동시에 사용하는 단계에서는 사용량 제한, 저장 큐, 오류 재시도, 교사별 로그인과 권한 분리를 추가한다.

| 생성형 AI API 연결 | 교사용 자료 분석·미리보기에는 Gemini를 사용할 수 있다. 학생용은 로컬 기본이며 승인된 외부 제공자만 서버에서 명시적으로 허용한다. |

| 소량 Supabase 사용 | Supabase에는 교사 ID, 수업 ID, 수업 코드, 암호화된 Gemini 키, 암호화된 Notion 토큰, 자동 탐색된 준비 DB/결과 DB 연결값, 생성일과 마감일만 저장한다. 학생 대화 본문과 평가 결과는 Notion DB에 저장한다. |

| 성취기준 분석 | 성취기준 문장을 핵심 성취, 내용 요소, 수행 행동, 평가 요소, 학생 산출물로 정리한다. |
| 루브릭 제작 | 질문하기, 지문 이해, 성취기준, 성찰질문과 의견 표현의 행동 증거를 0~5점으로 제시한다. |
| 루브릭 토글 | 교사용 보드에서는 전체 루브릭을 하나의 토글로 펼쳐 확인한다. |
| 이미지 자료 입력 | 교사가 이미지를 업로드하고 미리 볼 수 있다. |
| AI 자료 분석 | Gemini API 키가 있으면 이미지의 전체 텍스트를 요약 없이 추출한다. API 키가 없으면 교사가 전체 내용을 직접 입력해 사용할 수 있다. |
| 챗봇 제작 PRD | 교사용 보드의 4번 영역에서 학생용 챗봇에 반영할 수업 정보, 지식베이스, 루브릭, 기록 필드, 안전 규칙을 정리한다. |

| 상호작용 우선 응답 | 학생 말을 먼저 구체적으로 받아 주고 한 턴에 한 가지 도움을 준다. 질문은 유용할 때만 최대 한 개 사용한다. |

| 안전장치 | 개인정보, 정답 대필, 자료 밖 질문, 원문 전체 복사 요청을 제한한다. |

## 4-1. Notion 저장 아키텍처

Notion 기록은 Gemini가 아니라 웹앱 서버가 처리한다.

```text
학생 질문
→ 웹앱 서버 API
→ 서버 대화정책 판단
→ 로컬 또는 승인된 제공자 응답·분석 생성
→ 웹앱 서버가 Notion API로 결과 DB 저장
→ 학생에게 최소 `studentReply` 반환
```

교사용 준비 DB 저장도 같은 원칙을 따른다.

```text
교사용 보드 설정
→ 웹앱 서버 API
→ Notion API
→ 챗봇 수업 준비 DB 페이지 생성
```

고정 Notion DB 1개만 사용하는 1차 구현에 필요한 서버 환경변수는 다음과 같다.

```text
NOTION_API_KEY
NOTION_QUESTIONING_PREP_DATABASE_ID
NOTION_QUESTIONING_RESULT_DATABASE_ID
```

현재 권장 운영형에서는 위 값을 하나의 서버 환경변수로 고정하지 않고, 교사별 연결정보를 Supabase에서 조회한다. 교사는 교사용 보드에 Notion API 토큰만 입력하고, 웹앱 서버는 Integration이 연결된 템플릿에서 준비 DB와 결과 DB를 자동으로 찾는다. 이때 웹앱 서버에는 Supabase 접속용 서버 키와 암호화 키만 환경변수로 둔다.

```text
NEXT_PUBLIC_SUPABASE_URL
SUPABASE_SECRET_KEY
SUPABASE_SERVICE_ROLE_KEY
QUESTIONING_SECRET_ENCRYPTION_KEY
QUESTIONING_CONNECTION_SETUP_TOKEN
```

Gemini API 키, Notion API 토큰, 자동 탐색된 DB 연결값의 실제 값은 학생 브라우저, Gemini 프롬프트, PRD 본문, 공개 저장소에 포함하지 않는다.

## 4-2. 공통 웹앱 서버와 교사별 연결 구조

웹앱 서버는 교사가 쓰는 화면과 학생이 쓰는 화면을 제공하고, API 요청을 받아 각 교사의 Gemini·Notion 연결을 중계한다. 교사와 학생은 같은 배포 앱을 사용하지만, 수업 코드를 기준으로 서로 다른 설정을 불러온다.

```text
교사
→ 교사용 보드에서 Gemini 키와 Notion 토큰 입력
→ 웹앱 서버
→ Notion 템플릿의 준비 DB/결과 DB 자동 탐색
→ Supabase에 암호화된 연결정보 저장

학생
→ 학생용 챗봇에서 수업 코드와 학교·반·번호 입력
→ 웹앱 서버
→ Supabase에서 해당 수업 연결정보 조회
→ 로컬 자료 기반 응답 생성
→ 기관 승인과 서버 허용 시에만 승인된 외부 제공자 사용
→ 교사 개인 Notion 결과 DB에 학생 결과 저장
```

이 구조에서는 Vercel 웹앱을 교사별로 복제하지 않아도 된다. 교사마다 새로 생기는 것은 웹앱 프로젝트가 아니라 Notion 템플릿 복제본과 수업 코드이다. 웹앱 서버는 공통으로 유지하고, 수업별 차이는 Supabase의 연결정보와 교사 개인 Notion DB가 담당한다.

Supabase에 저장하는 최소 필드는 다음과 같다.

| 필드 | 용도 |
| --- | --- |
| `teacher_id` | 교사 또는 연수생 식별 |
| `lesson_id` | 수업 단위 식별 |
| `lesson_code` | 학생이 입력하거나 링크에 포함할 수업 코드 |
| `gemini_api_key_encrypted` | 교사 개인 Gemini 키 암호화 저장 |
| `notion_token_encrypted` | 교사 개인 Notion API 토큰 암호화 저장 |
| `prep_database_id` | 자동 탐색된 챗봇 수업 준비 DB 연결 |
| `result_database_id` | 자동 탐색된 챗봇 수업 결과 DB 연결 |
| `created_at`, `expires_at` | 생성일과 수업 종료/보관 기준 |

학생 질문, 챗봇 답변, 점수 근거, 세특용 피드백은 Supabase에 저장하지 않고 교사 개인 Notion 결과 DB에 저장한다.

## 5. 성취기준 분석 구조

성취기준은 바로 점수표나 매 턴의 목표로 바꾸지 않는다. 먼저 평가 가능한 언어로 풀어 쓰고, 학생 대화에서는 핵심 개념과 관찰 행동만 `curriculumCompass`로 제공한다.

기본 성취기준 선택지는 Notion 페이지 `2022 개정 교육과정 및 성취기준 분석 — 질문하기 수업·챗봇 활용`의 초3-4, 초5-6, 중1-3, 고등학교 국어·사회 성취기준을 바탕으로 구성한다.

| 분석 항목 | 내용 |
| --- | --- |
| 핵심 성취 | 이 수업에서 학생이 최종적으로 보여야 할 수행 |
| 내용 요소 | 학생 질문과 답이 다루어야 할 자료 내용 |
| 수행 행동 | 파악하기, 설명하기, 비교하기, 적용하기, 성찰하기 등 관찰 가능한 행동 |
| 평가 요소 | 루브릭 항목으로 바꿀 수 있는 판단 기준 |
| 학생 산출물 | 질문모음, 근거 확인 내용, 챗봇 답변모음, 질문을 다시 쓰고 바꾼 과정 등 평가할 증거 |

## 6. 평가 루브릭 구조

점수만 제시하지 않고, 교사가 실제 산출물에서 볼 수 있는 관찰 증거와 다음 피드백 방향을 함께 제공한다.

| 항목 | 관찰 증거 | 배점 |
| --- | --- | --- |
| 질문하기 | 1국면에서 학생이 스스로 질문을 만들고 이어 갔는가 | 0~5점 |
| 지문 이해 | 두 국면에서 낱말·사실·관계를 이해한 증거가 있는가 | 0~5점 |
| 성취기준 | 표적 신호가 든 질문과 성취기준 질문 응답이 있는가 | 0~5점 |
| 성찰질문과 의견 표현 | 마지막 질문에서 자기 생각을 자기 말로 표현했는가 | 0~5점 |

## 7. 챗봇 응답 규칙

1. 학생 발화가 질문이면 질문 자료의 구체적인 사실과 표현을 근거로 2-4문장으로 먼저 답한다.
2. 학생 발화가 이전 대화에 이어지는 대답이나 생각이면 그 의미를 구체적으로 받아 주고 앞선 대화와 연결한다.
3. 한 턴에는 설명, 반영, 근거 연결, 관점 확장, 낮은 부담의 단서, 불확실성 표시, 관계 회복, 안전 전환, 종료 중 한 가지 동작을 우선한다.
4. 질문은 학생 사고에 실제 도움이 되고 대화를 계속할 여지가 있을 때만 최대 한 개 사용한다. 최근 두 응답이 질문이었다면 이번에는 질문하지 않는다.
5. 학생이 짜증·거부·반복감을 표현하면 짧게 인정하거나 사과하고 선택권을 돌려준다. 이 턴에는 새 과제를 요구하지 않는다.
6. 학생이 `그만`, `됐어요`, `알겠어요`처럼 종료 의사를 보이면 질문 없이 자연스럽게 끝내고 `expectsStudentReply=false`로 처리한다.
7. 제목을 보고 내용을 예측하는 질문에는 제목을 그대로 반복하지 않고, 가능한 예상과 자료에서 확인할 부분을 구분한다.
8. 최근 대화를 참고해 같은 설명, 문장, 칭찬을 기계적으로 반복하지 않는다.
9. 답변에서는 사실·추론·적용·확장·성찰 같은 질문 유형 이름, 성취기준, 루브릭, 내부 상태를 말하지 않는다.
10. 질문 분류, 자료 근거 분석, 질문 개선 제안, 루브릭 점수, 대화 정책은 교사용 내부 데이터로만 생성한다.
11. 학생 화면에는 질문 자료를 표시하되 성취기준 원문, 교사 메모, 제작 PRD, API 키를 보내지 않는다.
12. 자료에는 없지만 수업 내용과 직접 관련 있는 질문에는 연결을 밝히고, 확인하지 못한 사실이나 출처를 지어내지 않는다.
13. 수업과 무관한 질문에는 범위를 짧게 알리고 자료로 돌아갈 수 있는 한 가지 선택지만 제시한다.
14. 학생 발화가 짧거나 막연하면 가능한 의미를 먼저 받아 주고, 부담이 작은 단서 하나를 제공한다.
15. 이름, 연락처, 사진 속 학생 식별 정보, 상담 정보 입력은 금지한다.
16. 활동지 정답 전체 작성이나 수행평가 대필은 거절하고 학생이 선택할 수 있는 작은 사고 단계만 안내한다.

## 9. 구현 메모

- 교사용 보드 경로: `/questioning-board`
- 학생용 챗봇 경로: `/questioning-chatbot`
- API 경로: `/api/questioning-board/analyze-image`, `/api/questioning-board/chat`, `/api/questioning-board/notion/preparation`, `/api/questioning-board/connections`
- Gemini 모델: `GEMINI_QUESTIONING_MODEL`, 없으면 `gemini-2.5-flash` 사용
- 서버 기본 Gemini 키: `GEMINI_API_KEY` (교사용 분석·미리보기)
- 학생용 외부 모델 허용: `QUESTIONING_STUDENT_LLM_ENABLED=true`와 `QUESTIONING_STUDENT_PROVIDER=approved_gemini`를 모두 명시한 경우에만 후보가 된다.
- 학생용 기본값: `QUESTIONING_STUDENT_LLM_ENABLED=false`, `QUESTIONING_STUDENT_PROVIDER=local`
- 교사용 보드에 입력한 Gemini 키는 교사용 기능에서만 사용하며 학생 컴포넌트는 브라우저 저장소의 키를 읽지 않는다.
- 운영형에서는 교사별 Gemini API 키와 Notion API 토큰을 Supabase의 `questioning_lesson_connections` 테이블에 암호화해 저장하고, 학생용 챗봇에는 수업 코드만 전달한다.
- Notion DB 환경변수가 설정되어 있으면 준비 내용과 학생 대화 결과를 Notion DB에 저장한다. 설정되어 있지 않으면 저장을 건너뛰고 기존 localStorage 흐름을 유지한다.
- 교사용 보드와 학생용 챗봇은 1차 구현에서는 같은 브라우저의 `localStorage` 설정으로 연결하고, 운영형에서는 수업 코드와 Supabase 연결정보로 연결한다.
- 교사용 보드에서 적용한 챗봇 동작 설정은 열려 있는 학생용 챗봇 탭에도 즉시 갱신한다.
- 학생용 챗봇은 최근 대화 8개를 API에 함께 보내 앞선 답과 자연스럽게 이어서 응답한다.
- 로컬 학생 응답과 승인된 외부 응답은 같은 `curriculumCompass`와 서버 대화정책을 사용한다. 기존 저장 데이터에 V2 설정이 없으면 안전한 기본값을 자동으로 보완한다.
- 평가 기록 엑셀에는 `평가 기록`, `성취기준 분석`, `루브릭`, `평가 기록 작성 기준` 시트를 포함한다.
- API 키가 없어도 교사가 질문 자료 전체 내용을 입력하면 학생용 로컬 대화, 내부 분류, 기록을 사용할 수 있다.
- 학생 API는 `studentReply`, `expectsStudentReply`, `isClosing` 중심의 최소 DTO만 반환하고 내부 정책·루브릭·교사 메모를 반환하지 않는다.
- 수업·세션 단위 요청 제한은 현재 분당 20회이며 단일 서버 메모리 기반의 최선형 보호다.

## 10. 현재 HTML 보드에서 Notion 연동형으로 확장하는 제안

현재 HTML 보드형 구현을 실제 수업 운영에 가깝게 확장하려면 아래 순서가 적절하다.

1. **노션 템플릿 복제**: 교사는 챗봇 수업 준비 DB와 챗봇 수업 결과 DB 템플릿을 복제한다.
2. **교사 개인 API 연결**: 교사는 자료 분석용 Gemini API 키와 결과 저장용 Notion API 토큰을 연결할 수 있다. 학생용 대화는 외부 모델 승인 없이도 로컬 모드로 작동한다.
3. **연결정보 저장**: 웹앱 서버는 제공된 교사 키와 Notion 토큰을 받고, Notion 템플릿에서 준비 DB와 결과 DB를 자동으로 찾은 뒤 연결정보를 암호화해 Supabase에 저장하고 수업 코드를 만든다.
4. **수업 준비 저장**: 교사용 보드에서 1, 2, 3, 4번을 작성하고 `노션 준비 DB에 저장`을 누르면 웹앱 서버가 교사 개인 Notion 준비 DB에 수업 준비 페이지를 만든다.
5. **학생 챗봇 적용**: 교사가 `현재 설정을 챗봇에 적용`을 누르면 학생용 챗봇은 같은 주소 `/questioning-chatbot`에서 수업 코드에 맞는 최신 자료와 루브릭을 사용한다.
6. **학생 식별 최소화**: 학생은 실명 없이 학교, 반, 번호만 입력한다.
7. **대화 결과 저장**: 학생이 질문하면 웹앱 서버가 수업 코드로 설정을 찾고 로컬 또는 승인된 응답과 내부 분석 결과를 만든 뒤 교사 개인 Notion 결과 DB의 `학교_반_번호` 페이지에 질문·답변·평가 분석·세특용 피드백을 누적한다.
8. **교사 환류**: 교사는 Notion 결과 DB에서 학생별 질문모음, 챗봇 답변모음, 점수 근거, 세특용 피드백을 확인하고 평가와 다음 수업 피드백으로 활용한다.
9. **내보내기 유지**: 엑셀 다운로드는 로컬 기록 양식으로 유지하되, 이후 Notion 결과 DB에 모인 학생 결과를 기준으로 내려받도록 확장한다.

가장 작은 1차 구현은 `localStorage` 연결을 유지하되, Notion 준비 DB 저장과 Notion 결과 DB 저장을 추가하는 방식이다. 운영형 1차 구현에서는 `questioning_lesson_connections` 테이블에 교사별 Gemini 키, Notion 토큰, 자동 탐색된 준비 DB/결과 DB 연결값, 챗봇 설정을 암호화 저장하고 수업 코드로 학생용 챗봇이 설정을 불러온다. 이후 로그인, 권한 분리, 수업별 만료 관리, 결과 조회 대시보드를 단계적으로 붙인다.

## 11. 운영 규모 기준

이 구조에서는 웹앱 서버가 모든 수업 데이터를 직접 보관하지 않는다. 웹앱 서버는 화면 제공, Gemini 호출 중계, Notion 저장 중계, 교사별 연결정보 조회만 담당한다. 따라서 연수 운영에서는 웹앱을 회차마다 복제하지 않아도 된다.

권장 기준은 다음과 같다.

| 규모 | 권장 판단 |
| --- | --- |
| 연수 1회차 30-40명 | 안정적이다. 공통 웹앱 1개와 소량 Supabase 저장으로 운영한다. |
