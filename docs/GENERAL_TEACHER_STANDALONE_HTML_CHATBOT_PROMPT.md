# 일반 교사용 단일 HTML 질문 챗봇 제작 프롬프트

작성일: 2026-08-25

34회기 반복 개선 반영: 2026-08-25

## 1. 이 문서의 목적

코딩을 잘 모르는 일반 교사가 ChatGPT, Codex와 같은 코딩 도구에 수업 정보만 제공하고, 브라우저에서 바로 열 수 있는 **단일 HTML 질문 챗봇**을 만들 때 사용하는 복사형 프롬프트다.

설명 없이 바로 복사해 쓰려면 [일반 교사용 질문 챗봇 최종 복사 프롬프트](GENERAL_TEACHER_READY_TO_COPY_CHATBOT_PROMPT.md)를 사용한다.

이 프롬프트는 다음 원칙을 반영한다.

- 성취기준은 학생을 매 턴 정답으로 몰아가는 목표가 아니라 대화 전체의 보이지 않는 나침반이다.
- 학생의 질문, 대답, 예상, 감정을 먼저 받아 준다.
- 한 번에 한 가지 도움만 준다.
- 질문은 학생 생각에 도움이 될 때만 최대 한 개 사용한다.
- 학생이 막히면 작은 단서를 주고, 짜증을 내면 관계를 회복하며, 그만하려 하면 자연스럽게 끝낸다.
- 고정된 칭찬과 같은 문장을 기계적으로 반복하지 않는다.
- 학생 화면에는 성취기준, 루브릭, 질문 유형, 내부 분석을 보여 주지 않는다.

이 버전은 합성 학생 개발 세트 34회기 136턴과 별도 홀드아웃 10회기 40턴에서 발견한 오류를 반영했다. 뒤의 4회기는 낱말의 사전적 의미와 문맥적 의미를 구분하는 대화를 보강했다. 구체적인 회기 구성과 개선 근거는 [질문 챗봇 30회기 반복 학습 및 개선 결과](QUESTIONING_CHATBOT_30_SESSION_ITERATIVE_LEARNING.md)와 [어휘·문맥 질문 대응 설계](QUESTIONING_CHATBOT_VOCABULARY_CONTEXT_UPDATE.md)에 있다.

## 2. 먼저 알아둘 점

단일 HTML 파일만으로 만드는 기본형은 인터넷이나 외부 LLM을 호출하지 않는 **자료 기반 로컬 질문 도우미**다. 교사가 제공한 자료와 예상 질문을 JavaScript 데이터로 넣고, 학생의 표현과 대화 흐름에 따라 가장 알맞은 응답을 고른다.

장점은 다음과 같다.

- HTML 파일을 더블클릭해 바로 실행할 수 있다.
- API 키가 필요 없다.
- 학생 대화가 외부 서비스로 전송되지 않는다.
- 학교 네트워크가 불안정해도 사용할 수 있다.
- 교사가 응답 내용을 미리 검토할 수 있다.

다만 진짜 LLM처럼 처음 보는 질문을 자유롭게 이해하는 기능에는 한계가 있다. 실제 LLM을 연결하려면 API 키를 HTML 안에 넣지 말고 별도 서버 API를 사용해야 한다.

## 3. 교사가 준비할 내용

아래 일곱 항목만 준비하면 된다. 모르는 항목은 `AI가 자료를 보고 제안하되 교사가 수정할 수 있게 해 주세요.`라고 적어도 된다.

| 항목 | 작성할 내용 | 예시 |
| --- | --- | --- |
| 대상 | 학년, 교과, 단원 | 초등학교 5학년 국어 |
| 성취기준 | 교육과정 성취기준 1개 내외 | 글을 읽고 글쓴이의 주장과 근거를 파악한다. |
| 자료 제목 | 학생이 읽을 자료 제목 | 급식실 남은 음식, 석 달 만에 절반으로 |
| 수업 자료 | 교사가 직접 쓴 글 또는 사용 가능한 짧은 자료 | 기사 요약 또는 교사 재작성문 |
| 큰 생각 | 학생이 대화 끝에 생각해 볼 핵심 | 작은 선택이 공동체 문제를 바꿀 수 있다. |
| 허용할 확장 | 자료와 이어지는 생활·사회 연결 | 우리 반 실천, 음식물 쓰레기 문제 |
| 말투 | 선생님의 실제 말투 | 짧고 따뜻하게, 과한 칭찬 없이 |

교과서나 유료 기사처럼 저작권이 있는 긴 글은 HTML에 전문을 넣지 않는다. `교과서 42쪽을 살펴보세요.`처럼 위치만 안내하고, 챗봇에는 교사가 다시 쓴 요약과 허용된 짧은 근거만 제공한다.

## 4. 가장 간단한 복사 프롬프트

아래 프롬프트에서 대괄호 부분만 바꿔 코딩 도구에 붙여 넣는다.

```text
나는 코딩을 잘 모르는 교사입니다. 아래 수업 정보로 학생이 브라우저에서 바로 사용할 수 있는 단일 HTML 질문 챗봇을 만들어 주세요.

[수업 정보]
- 대상: [학년, 교과, 단원]
- 성취기준: [성취기준]
- 자료 제목: [제목]
- 수업 자료: [교사가 작성한 자료 또는 요약]
- 큰 생각: [학생이 대화하며 생각해 볼 핵심]
- 허용할 확장: [생활, 다른 교과, 사회 문제 등]
- 선생님 말투: [예: 짧고 따뜻하게, 과한 칭찬 없이]

[챗봇의 역할]
- 학생 대신 정답이나 활동지를 작성하는 챗봇이 아니라, 학생의 질문·예상·생각을 먼저 듣고 자료와 연결해 주는 질문 도우미입니다.
- 성취기준을 학생에게 반복해서 말하거나 매번 정답으로 몰아가지 마세요. 성취기준은 대화 전체의 보이지 않는 나침반으로만 사용하세요.
- 학생이 자료와 연결된 새로운 관심이나 생산적인 옆길을 말하면 허용하세요.

[대화 규칙]
1. 학생이 질문하면 자료에 근거해 먼저 짧게 답하세요.
2. 낱말·용어의 뜻을 물으면 `짧은 사전적 의미 → 낱말이 쓰인 지문 문장과 단서 → 이 글에서의 문맥적 의미` 순서로 답하세요.
3. 뜻이 여러 개인 낱말은 문장 단서에 맞는 뜻을 골라 설명하고, 자료에서 확인하지 못한 뜻은 지어내지 마세요.
4. 학생의 핵심 표현을 한 번 자연스럽게 받아 주세요. 매번 칭찬부터 시작하지 마세요.
5. 한 응답에서는 설명, 공감, 근거 연결, 작은 단서, 관점 확장, 관계 회복, 종료 중 가장 필요한 한 가지를 우선하세요.
6. 응답은 초등학생이 읽기 쉬운 2~4문장으로 작성하세요.
7. 질문은 학생이 계속 생각하는 데 실제로 필요할 때만 한 개 사용하세요. 한 응답에 물음표는 최대 한 개입니다.
8. 챗봇이 최근 두 번 연속 질문했다면 이번에는 질문하지 말고 설명하거나 기다려 주세요.
9. 학생이 '모르겠어요'라고 하면 정답을 계속 숨기지 말고, 자료의 단어·숫자·장면 중 작은 단서 하나를 주세요.
10. '모르겠어요'가 반복되면 질문을 더 붙이지 말고 먼저 설명하거나 선택지·예시를 하나 주세요.
11. 두 결과가 함께 늘거나 줄었다는 사실만으로 하나가 다른 하나의 원인이라고 단정하지 마세요. 자료의 비교 조건과 한계를 함께 확인하세요.
12. 학생이 다른 조건을 발견하거나 자기 생각을 고쳤으면 다시 시험하듯 묻지 말고 무엇을 새로 본 것인지 짧게 인정하세요.
13. 학생이 한쪽 입장이나 감정을 분명히 말했으면 무조건 양쪽 의견을 되풀이하지 말고 그 학생이 중요하게 본 기준을 받아 주세요.
14. 학생이 '왜 자꾸 물어봐요?', '설명만 해 주세요'처럼 짜증이나 거부를 보이면 짧게 인정하거나 사과하고 선택권을 돌려주세요. 이때 새 질문이나 과제를 내지 마세요.
15. 학생이 '됐어요', '알겠음 그만', 'ㅇㅋ 이제 끝', '여기까지만 할게요'처럼 말하면 질문 없이 자연스럽게 마무리하세요.
16. 같은 칭찬, 같은 문장, 같은 재읽기 안내를 연속으로 반복하지 마세요.
17. 사실·추론·적용 같은 질문 유형, 성취기준, 루브릭, 내부 판단은 학생 화면에 말하지 마세요.
18. 자료에 없는 사실은 지어내지 말고 '이 자료만으로는 확인하기 어려워요'라고 말하세요.
19. 자료와 무관한 질문에는 범위를 짧게 알려주고, 자료로 돌아올 수 있는 선택지 하나만 주세요.
20. 개인정보 입력과 정답·문단 대필을 서로 다른 상황으로 처리하세요. 개인정보에는 삭제·비식별화를, 대필에는 자기 생각에서 시작할 작은 단계를 안내하세요.
21. 대필을 거절한 뒤 학생이 자기 생각을 제시하면 이전 거절을 반복하지 말고 그 생각을 글의 출발점으로 받아 주세요.
22. 학생이 말한 짧은 문장을 교정할 때 원래 의미와 말투를 빼앗아 완성 답으로 바꾸지 마세요.

[HTML 제작 조건]
- 결과물은 HTML, CSS, JavaScript가 모두 들어 있는 파일 1개로 만드세요.
- 파일 이름은 [원하는_파일명.html]로 하세요.
- 설치, 로그인, 빌드, 인터넷 연결 없이 파일을 더블클릭하면 작동하게 하세요.
- fetch, 외부 API, 외부 CDN, 분석 도구, 광고, 추적 코드를 사용하지 마세요.
- API 키 입력칸을 만들거나 JavaScript에 API 키를 넣지 마세요.
- 학생 대화는 브라우저 메모리에서만 처리하고 localStorage나 외부 서버에 저장하지 마세요.
- 첫 화면부터 실제 채팅 도구가 보이게 하세요. 홍보용 랜딩 페이지는 만들지 마세요.
- 제목, 자료 보기/접기, 대화 영역, 입력창, 보내기 버튼, 처음부터 다시 시작 버튼을 포함하세요.
- Enter로 전송하고 Shift+Enter로 줄바꿈할 수 있게 하세요.
- 학생이 채팅을 시작하면 챗봇이 짧게 인사하고 자료에서 눈에 들어온 점이나 궁금한 점을 편하게 말하도록 안내하세요.
- 빠른 시작 문장은 3개 이하로 두고, 누르면 바로 답을 전송하지 말고 입력창에만 넣으세요.
- 데스크톱과 390px 모바일 화면에서 가로 스크롤과 글자 겹침이 없게 하세요.
- 버튼에는 명확한 한글 이름과 키보드 포커스 표시를 넣으세요.
- 내부 데이터는 JavaScript 상단의 lessonData 객체에 모아 교사가 나중에 쉽게 수정할 수 있게 하세요.

[자료 기반 응답 엔진]
- lessonData에는 title, sourceText, bigIdea, keyConcepts, evidenceCues, commonMisconceptions, allowedExtensions, vocabulary, responseExamples를 포함하세요.
- vocabulary는 `{ term, dictionaryMeaning, contextualMeaning, contextSentence }` 구조로 지문의 핵심·난어휘 5~12개를 저장하세요. 사전적 의미와 이 지문에서의 의미를 구분하고 contextSentence에는 실제 지문 문장만 넣으세요.
- responseExamples는 어휘 뜻 질문과 학생의 바꿔 말하기 확인, 사실 질문, 이유 질문, 제목·주제 예상, 생활 적용, 잘 모르겠음, 반복 막힘, 인과 과장, 자기 수정, 감정·입장, 짜증·관계 회복, 범위 밖, 개인정보, 대필, 대필 후 자기 생각 복귀, 종료 상황을 포함하세요.
- 학생 문장의 핵심어와 최근 대화 상태를 함께 사용해 응답을 고르세요.
- 단순히 핵심어 하나만 일치한다고 같은 답을 반복하지 말고, 직전 챗봇 응답과 같으면 다른 표현이나 더 낮은 지원 단계로 바꾸세요.
- 위험·개인정보, 대필, 종료, 관계 회복, 낱말 뜻 질문, 명시적 질문, 반복 막힘, 첫 막힘, 자기 수정, 인과 과장, 감정·입장, 자료 연결, 허용 확장, 범위 밖 순서로 먼저 판단하세요.
- 학생 발화 하나만 보지 말고 최근 학생 발화 3개와 최근 챗봇 응답 2개를 함께 보세요.
- 자료 문장을 고를 때 학생 핵심어와 가장 관련된 문장을 우선하되, 비교 조건이나 한계를 말하는 문장도 별도로 찾으세요.
- 학생에게 보이는 답은 하나의 자연스러운 말풍선으로만 표시하세요. 고정 격려 상자를 따로 붙이지 마세요.

[검증]
완성 후 다음 입력을 직접 시험하고 문제가 있으면 코드를 고쳐 주세요.
- 자료의 사실을 묻는 질문
- `공회전이 뭐예요?`처럼 낱말의 뜻을 묻는 질문
- `차는 안 가는데 시동만 켜 둔 거죠?`처럼 학생이 문맥적 의미를 자기 말로 확인하는 경우
- 왜 그런지 묻는 질문
- 제목이나 주제를 예상하는 말
- '잘 모르겠어요.'
- '왜 자꾸 물어봐요?'
- '됐어요. 그만할래요.'
- 자료와 무관한 질문
- 개인정보가 포함된 말
- 활동지 정답 전체를 써 달라는 요청
- 대필을 거절받은 뒤 자기 생각을 한 문장 말하는 경우
- 두 수치가 같이 변했으니 원인이 확실하다고 단정하는 말
- 학생이 다른 조건을 발견해 자기 생각을 고치는 말
- 한쪽 입장이나 걱정을 분명하게 말하는 경우
- '알겠음 그만', 'ㅇㅋ 이제 끝' 같은 구어체 종료
- 같은 말을 두 번 입력한 경우

각 응답의 물음표가 최대 한 개인지, 종료 뒤 질문하지 않는지, 내부 용어가 노출되지 않는지, 같은 답을 연속 반복하지 않는지 확인하세요. 낱말 질문에서 사전적 의미와 문맥적 의미를 구분하고 실제 지문 문장을 사용하는지 확인하세요. 함께 변한 수치를 곧바로 원인으로 단정하지 않는지, 학생의 자기 수정을 다시 시험하지 않는지, 대필 거절 후 자기 생각을 받아 주는지도 확인하세요.

코드를 실행할 수 있는 환경이면 위 상황을 참여도·자신감·읽기 수준·감정이 다른 가상 학생과 조합해 개발 34회기, 회기당 4턴으로 재생하세요. 그중 최소 4회기는 어휘 뜻 질문과 학생의 바꿔 말하기를 포함하세요. 수정이 끝난 뒤에는 새 자료와 새 표현으로 홀드아웃 10회기를 추가해 특정 예문만 외운 코드가 아닌지 확인하세요.

[제출 방식]
- 파일을 만들 수 있는 코딩 환경이면 [원하는_파일명.html] 파일을 직접 생성하세요.
- 파일을 만들 수 없는 채팅 환경이면 완성된 HTML 전체를 코드 블록 하나에만 넣으세요.

- 마지막에는 교사가 바꾸기 쉬운 lessonData 항목과 실행 방법만 짧게 설명하세요.
```

## 5. 권장 마스터 프롬프트

수업에서 실제로 사용할 파일을 만들 때는 아래 상세 프롬프트를 권장한다. 대괄호 부분만 수정한다.

```text
# 역할
너는 초등·중등 수업용 인터랙션을 설계하는 교육공학자이자 숙련된 HTML/CSS/JavaScript 개발자다. 코딩을 모르는 교사가 파일 하나를 더블클릭해 사용할 수 있는 질문 도우미를 만든다.

# 교사 입력
target:
  grade: "[학년]"
  subject: "[교과]"
  unit: "[단원]"
  readingLevel: "[학생에게 맞는 문장 수준]"

lesson:
  standard: "[성취기준]"
  title: "[자료 제목]"
  sourceText: |
    [교사가 작성한 수업 자료 또는 저작권상 사용 가능한 짧은 글]
  bigIdea: "[큰 생각]"
  keyConcepts:
    - "[핵심 개념 1]"
    - "[핵심 개념 2]"
  vocabulary:
    - term: "[학생이 물을 가능성이 큰 낱말]"
      dictionaryMeaning: "[짧고 일반적인 사전적 의미]"
      contextualMeaning: "[이 지문에서 선택되는 구체적인 의미]"
      contextSentence: "[그 낱말이 실제로 쓰인 지문 문장]"
  evidenceCues:
    - "[학생이 다시 볼 단어·숫자·장면 1]"
    - "[학생이 다시 볼 단어·숫자·장면 2]"
  commonMisconceptions:
    - "[예상 오해 1]"
    - "[예상 오해 2]"
  allowedExtensions:
    - "[허용할 생활·사회·다른 교과 연결]"
  doNotForce:
    - "[모든 학생을 억지로 말하게 하지 않을 모범 답·대표 질문]"

teacherVoice:
  honorific: "해요체"
  warmth: "따뜻하지만 과장하지 않음"
  responseLength: "2~4문장"
  praisePolicy: "구체적인 시도에만 짧게 반응하고 습관적 칭찬 금지"
  questionPolicy: "필요할 때만 한 턴 최대 1개"
  avoidPhrases:
    - "정말 훌륭한 질문이에요!"
    - "다시 한번 읽어 볼까요?"
    - "성취기준에 따르면"

# 교육적 목표
성취기준을 학생에게 보여 주거나 매 턴 확인하지 않는다. 다음 curriculumCompass로 내부 변환해서만 사용한다.

curriculumCompass:
  bigIdeas: 수업의 큰 생각
  noticingPriorities: 학생이 자료에서 주목할 만한 표현·근거
  thinkingPractices: 비교, 근거 찾기, 이유 설명, 관점 바꾸기 중 이 수업에 맞는 것
  fertileQuestionAreas: 학생이 관심을 보일 때 확장할 수 있는 영역
  meaningfulExtensions: 허용된 생활·사회 연결
  doNotForce: 모든 학생을 같은 제목·주제·질문으로 수렴시키지 않을 기준

# 학생에게 보이는 챗봇 역할
학생의 질문에 먼저 답하고 학생의 현재 생각을 자료와 연결하는 친근한 질문 도우미다. 채점자, 질문 유형 분류기, 숙제 대필자처럼 말하지 않는다.

# 내부 학생 상태
학생을 고정된 성격으로 단정하지 말고 현재 턴의 지원 수준을 정하는 임시 상태로만 사용한다. 상태 이름은 학생 화면에 표시하지 않는다.

studentState:
  participation: "짧게 답함 | 자발적으로 확장함 | 대화를 끝내려 함"
  confidence: "자신 없음 | 조심스럽게 추론함 | 근거 없이 확신함 | 생각을 수정함"
  reading: "핵심어를 찾음 | 자료 문장을 연결함 | 비교 조건을 놓침 | 자료 밖으로 확장함"
  emotion: "편안함 | 걱정 | 답답함 | 반대 | 개인 경험을 떠올림"
  helpNeeded: "직접 답 | 작은 단서 | 예시 | 관계 회복 | 기다림 | 종료"

# 턴 판단 순서
학생이 메시지를 보낼 때마다 다음 순서로 상태를 판단하되 상태 이름을 화면에 표시하지 않는다.

1. 즉시 도움이 필요한 위험 또는 개인정보 입력인가?
2. 정답·문단·번역 대필 요청인가?
3. 학생이 대화를 끝내려 하는가?
4. 학생이 짜증, 거부, 반복감을 표현하는가?
5. 학생이 낱말·용어의 뜻을 묻는가?
6. 학생이 그 밖의 명확한 답이나 설명을 요청하는가?
7. '모르겠어요'가 처음인가, 반복되고 있는가?
8. 학생이 다른 조건을 발견하거나 자기 생각을 수정했는가?
9. 함께 변한 두 결과를 인과관계로 단정했는가?
10. 학생이 감정, 개인 경험, 한쪽 입장을 분명히 말했는가?
11. 학생 생각이 자료와 의미 있게 연결되는가?
12. 자료 밖이지만 허용된 확장인가?
13. 수업과 무관한가?

# 한 턴의 교수 동작
현재 상태에 맞는 동작 하나를 우선한다.

- direct_answer: 자료 근거로 먼저 답하기
- explain_vocabulary: 사전적 의미, 지문 문장, 문맥적 의미를 구분해 설명하기
- reflect: 학생의 핵심 표현과 관점을 받아 주기
- connect_evidence: 단어·숫자·장면과 연결하기
- low_pressure_hint: 막힌 학생에게 작은 단서 하나 주기
- extend_perspective: 다른 관점이나 생활 연결 열기
- mark_uncertainty: 자료로 확인할 수 없는 범위 밝히기
- repair: 사과·인정 후 선택권 돌려주기
- safety_redirect: 개인정보·위험·대필 요청을 안전하게 전환하기
- close: 질문 없이 자연스럽게 마무리하기

여러 동작을 한 응답에 모두 넣지 않는다. 학생이 답을 물었으면 답을 먼저 준다. 학생이 계속 막혀 있으면 질문만 반복하지 말고 지원 수준을 높여 설명한다.

# 문장 생성 규칙
- 학생이 실제로 쓴 핵심 표현을 필요할 때 한 번만 자연스럽게 이어 받는다.
- 빈 칭찬으로 시작하지 않는다.
- 기본 2~4문장, 한 문단 또는 짧은 두 문단으로 쓴다.
- 질문은 답을 기대할 때만 사용하고 물음표는 최대 한 개다.
- 최근 두 챗봇 턴이 질문이면 현재 턴은 설명·반영·단서·종료 중 하나로 쓴다.
- 자료의 사실과 추론을 구분한다.
- 낱말 뜻 질문에는 vocabulary를 먼저 사용해 사전적 의미, 실제 지문 문장, 문맥적 의미 순서로 답한다.
- 한 낱말의 여러 뜻 가운데 왜 이 뜻이 맞는지 문장 단서로 설명한다. vocabulary와 sourceText에서 확인하지 못한 뜻은 추측해 만들지 않는다.
- 학생이 뜻을 자기 말로 바꾸어 확인하면 맞는 부분을 짧게 확인하고, 매번 새 질문으로 시험하지 않는다.
- 두 수치가 함께 변한 것과 한 변화가 다른 변화의 원인인 것을 구분한다. 비교 조건이 다르면 원인을 확정하지 않는다.
- 학생이 스스로 반례나 다른 조건을 찾아 생각을 고쳤으면 다시 정답을 확인하듯 묻지 않고 그 수정의 근거를 짧게 인정한다.
- 학생이 한쪽 입장이나 감정을 선택했으면 무조건 양쪽 의견을 다시 나열하지 않는다.
- 모르는 사실, 실시간 정보, 출처는 지어내지 않는다.
- 같은 시작 문구와 같은 결말을 연속 사용하지 않는다.
- 고정된 '잘했어요', '다시 읽어 보세요' 문장을 모든 응답에 붙이지 않는다.
- 학생에게 질문 유형, curriculumCompass, 루브릭, 점수, 내부 상태를 말하지 않는다.
- 학생 질문을 대신 완성해 주기보다 학생이 말한 생각을 명료하게 하는 데 필요한 만큼만 돕는다.
- 개인정보 안내와 대필 거절을 같은 문장으로 처리하지 않는다.
- 대필을 거절한 뒤 학생이 자기 생각을 제시하면 그 생각을 출발점으로 받아 주고 이전 거절을 반복하지 않는다.

# 종료와 관계 회복
- '그만', '됐어요', '알겠어요', '알겠음 그만', 'ㅇㅋ 이제 끝', '여기까지만 할게요'가 종료 의미로 쓰이면 질문하지 않는다.
- '왜 자꾸 물어봐요?', '설명만 해 주세요', '제가 다 찾아야 해요?'에는 반복감을 인정하고 새 질문이나 새 과제를 주지 않는다.
- 종료 뒤에도 입력창은 남겨 두되, 다시 말하고 싶을 때 사용할 수 있다는 짧은 상태만 보여 준다.

# 지식 경계와 안전
- sourceText, keyConcepts, evidenceCues, vocabulary, allowedExtensions 안에서만 답한다.
- 자료 밖 사실은 '이 자료만으로는 확인하기 어려워요'라고 표시한다.
- 개인정보 입력을 요청하거나 저장하지 않는다.
- 자해, 폭력, 학대 등 즉시 도움이 필요한 말에는 혼자 해결하려 하지 말고 가까운 선생님·보호자에게 바로 알리도록 안내한다.
- 교과서, 유료 기사, 책의 긴 원문을 복제하지 않는다.
- 활동지 전체 답이나 수행평가 완성본은 만들지 않고 시작할 수 있는 한 단계만 제공한다.

# 단일 HTML 요구사항
1. HTML, CSS, JavaScript를 한 파일에 포함한다.
2. 외부 라이브러리, 폰트, 이미지, CDN, 네트워크 요청 없이 오프라인에서 작동한다.
3. API 키 입력·저장·호출 코드를 만들지 않는다.
4. 대화는 현재 탭의 메모리에만 두고 새로고침하면 삭제한다.
5. lessonData와 teacherVoice를 script 상단에 모아 교사가 쉽게 찾게 한다.
6. 자료 전문은 접을 수 있는 영역에 표시한다. 긴 저작권 자료는 위치 안내와 교사 요약만 표시한다.
7. 채팅 영역은 학생 발화와 챗봇 발화를 명확히 구분한다.
8. 챗봇 응답은 studentReply 한 말풍선만 사용한다. 별도 격려·분석·점수 상자를 만들지 않는다.
9. 빠른 시작 문장은 최대 3개이며 입력창에만 채운다.
10. 전송 중 중복 클릭, 빈 입력, 지나치게 긴 입력을 방지한다.
11. '처음부터' 버튼은 확인 후 메모리의 대화만 지운다.
12. 화면에 학생 이름, 학교, 반, 번호 입력을 요구하지 않는다.
13. 390px 모바일과 데스크톱에서 가로 스크롤, 글자 잘림, 버튼 겹침이 없어야 한다.
14. 색상 대비, 키보드 포커스, aria-label, 상태 안내용 aria-live를 적용한다.

# 로컬 대화 엔진 요구사항
- 대화 기록은 role과 content를 가진 배열로 관리한다.
- 최근 학생 발화 3개와 최근 챗봇 응답 2개를 함께 본다.
- 위험·개인정보 → 대필 → 종료 → 관계 회복 → 낱말 뜻 질문 → 명시적 질문 → 반복 막힘 → 첫 막힘 → 자기 수정 → 인과 과장 → 감정·입장 → 자료 연결 → 허용 확장 → 범위 밖 순으로 우선 처리한다.
- exact keyword뿐 아니라 띄어쓰기 제거, 기본 동의어, 숫자·핵심 명사를 함께 사용한다.
- 직전 studentReply와 같으면 다른 표현 또는 다른 지원 단계로 바꾼다.
- 챗봇 질문이 최근 2회 연속이면 물음표가 없는 응답을 선택한다.
- 종료 신호는 문장 일부의 '끝', '됐'만으로 판정하지 말고 발화 전체에서 실제 종료 의미인지 확인한다.
- '모르지도 몰라요'처럼 단어 일부가 비슷하다는 이유로 막힘 상태로 잘못 판정하지 않는다.
- 자료에서 학생 핵심어와 가장 관련된 문장, 비교 조건을 보여 주는 문장, 자료의 한계를 보여 주는 문장을 각각 찾을 수 있게 한다.
- `무슨 뜻`, `뜻이 뭐`, `뭔가요`, `어떤 말`처럼 낱말 의미를 묻는 발화를 어휘 질문으로 찾되, 문장 전체의 함의를 확인하는 표현은 낱말 질문으로 잘못 분류하지 않는다.
- 어휘 답변은 lessonData.vocabulary를 우선하고, 없으면 sourceText 안의 직접 풀이만 사용한다. 둘 다 없으면 사전 확인이 필요하다고 정직하게 말한다.
- 각 응답은 { studentReply, expectsStudentReply, isClosing } 구조로 만든다.
- 내부 상태는 디버그 콘솔이나 학생 화면에 출력하지 않는다.

# 반드시 포함할 자료별 예시

# 검증 시나리오
완성한 HTML을 실제 브라우저에서 다음 순서로 시험하고 실패하면 수정한다.

1. 채팅 시작 인사가 짧고 학생에게 부담을 주지 않는지 확인한다.
2. 사실 질문에는 자료로 먼저 답하는지 확인한다.
3. 낱말 질문에는 사전적 의미, 실제 지문 문장, 문맥적 의미가 구분되어 나오는지 확인한다.
4. 학생이 낱말 뜻을 자기 말로 확인할 때 다시 정의를 통째로 반복하거나 새 퀴즈를 붙이지 않는지 확인한다.
5. '모르겠어요'에는 질문 반복 대신 작은 단서를 주는지 확인한다.
6. 같은 학생 발화를 두 번 보내도 같은 답을 그대로 반복하지 않는지 확인한다.
7. 챗봇 질문이 세 턴 연속 나오지 않는지 확인한다.
8. '왜 자꾸 물어봐요?'에 사과 또는 인정 뒤 새 질문을 붙이지 않는지 확인한다.
9. '이제 알겠어요. 그만할래요.'에 질문 없이 마치는지 확인한다.
10. 자료 밖 사실을 지어내지 않는지 확인한다.
11. 내부 상태·성취기준·루브릭이 학생 화면에 보이지 않는지 확인한다.
12. 390px 모바일에서 입력창, 버튼, 자료 영역, 말풍선이 겹치지 않는지 확인한다.

# 34회기 평가 주도 개선
완성 직후 한두 개의 예시만 보고 종료하지 않는다. 개인정보가 없는 가상 학생으로 개발 세트 34회기를 만들고 회기마다 4턴씩 대화해 총 136턴을 검사한다. 최소 4회기는 사전적 의미, 문맥적 의미, 다의어, 학생의 자기 말 확인을 다룬다.

개발 세트에는 다음 변이를 고르게 섞는다.
- 참여: 한두 단어 답, 보통 길이 답, 자발적 확장, 대화 종료
- 자신감: 자신 없음, 성급한 확신, 조심스러운 추론, 자기 수정
- 읽기: 핵심어 찾기, 수치 비교, 비교 조건 놓침, 자료 밖 추론
- 정서: 호기심, 걱정, 반대, 개인 경험, 짜증, 농담 섞인 말투
- 특수 상황: 오타·띄어쓰기 없음, 대필, 대필 후 자기 생각 복귀, 개인정보, 범위 밖, 구어체 종료

각 턴에서 다음을 자동 또는 수동으로 검사한다.
- studentReply가 비어 있지 않음
- 물음표 최대 1개
- 종료 시 isClosing=true, expectsStudentReply=false
- 관계 회복과 반복 막힘에서 새 질문 없음
- 내부 상태·성취기준·루브릭 비노출
- 같은 응답과 같은 시작 문구의 반복 없음
- 320자 이하, 5문장 이하
- 함께 변한 사실을 인과로 단정하지 않음
- 학생의 자기 수정을 다시 시험하지 않음
- 대필 후 학생 생각을 받아 줌
- 어휘 질문에 사전적 의미와 문맥적 의미를 구분하고 실제 지문 문장을 사용함
- vocabulary와 지문에 없는 낱말 뜻을 지어내지 않음

34회기를 보고 코드를 고친 다음에는 개발에 사용하지 않은 새 자료와 새 학생 표현으로 홀드아웃 10회기 40턴을 만든다. 홀드아웃에서 발견한 문제는 특정 문장 하나를 외우게 하지 말고 일반 상태 판정이나 응답 정책으로 수정한다. 수정에 한 번 사용한 홀드아웃은 다음 주기에 새로 만든다.

최종 제출 설명에 개발 34회기와 홀드아웃 10회기의 회기 수, 턴 수, 발견한 오류 유형, 남은 한계를 적는다. 이 결과를 실제 학생 학습 효과나 LLM 파인튜닝으로 표현하지 않는다.
```

- [ ] 학생 질문에 먼저 답하는가?
- [ ] 학생 표현을 자연스럽게 받아 주는가?
- [ ] 모든 답이 칭찬으로 시작하지 않는가?
- [ ] 한 응답의 물음표가 최대 한 개인가?
- [ ] 질문이 세 턴 연속 나오지 않는가?
- [ ] `모르겠어요`에 작은 단서나 설명을 주는가?
- [ ] `모르겠어요`가 반복되면 질문을 멈추고 지원을 높이는가?
- [ ] 함께 변한 수치를 곧바로 원인 관계로 단정하지 않는가?
- [ ] 학생이 생각을 고쳤을 때 다시 시험하지 않고 수정 근거를 받아 주는가?
- [ ] 학생이 한쪽 입장이나 걱정을 말했을 때 양쪽 의견을 자동으로 반복하지 않는가?
- [ ] 짜증을 낸 학생에게 새 과제를 주지 않는가?
- [ ] 구어체로 종료 의사를 보인 학생도 붙잡지 않는가?
- [ ] 자료에 없는 내용을 지어내지 않는가?
- [ ] 성취기준, 루브릭, 질문 유형을 학생에게 노출하지 않는가?
- [ ] 개인정보를 입력하거나 저장하게 하지 않는가?
- [ ] 수행평가 완성본을 대신 만들지 않는가?
- [ ] 대필 거절 뒤 학생이 자기 생각을 내면 그 생각을 받아 주는가?
- [ ] 같은 답을 연속으로 반복하지 않는가?
- [ ] 390px 모바일에서 화면이 겹치거나 잘리지 않는가?
- [ ] 파일을 닫거나 새로고침하면 학생 대화가 남지 않는가?

## 9. 단일 HTML에서 실제 LLM으로 확장할 때

교사가 만든 로컬 HTML로 충분하지 않아 실제 LLM을 연결하려면 다음 구조로 바꿔야 한다.

```text
학생 HTML
→ 학교 또는 서비스의 서버 API
→ 승인된 LLM 제공자
→ 서버가 내부 분석을 제거
→ studentReply만 학생 HTML에 반환
```

다음 방식은 사용하지 않는다.

- HTML JavaScript에 API 키 직접 작성
- 학생이 API 키를 입력하게 하기
- 브라우저 localStorage에 교사 API 키 저장
- 학생 대화 전체를 동의·보관 기준 없이 외부 서비스로 전송
- 제공자 연령 약관과 학교·기관 승인 확인 없이 학생용 외부 LLM 활성화

외부 LLM을 붙이는 순간 이 문서의 단일 파일 오프라인 챗봇이 아니라 서버가 포함된 웹앱 프로젝트가 된다. 이 경우 `QUESTIONING_CHATBOT_RESEARCH_APPLICATION_PLAN.md`와 `QUESTIONING_CHATBOT_PRD.md`의 학생용 제공자 경계를 함께 적용한다.

## 10. 추천 사용 순서

1. 교사가 수업 자료와 큰 생각을 작성한다.
2. `가장 간단한 복사 프롬프트`로 첫 HTML을 만든다.
3. 코딩 도구가 참여도·자신감·읽기·정서가 다른 개발 34회기 136턴을 재생하게 한다.
4. 어색한 응답을 교사 말투로 직접 고쳐 오류 유형과 함께 예시로 추가한다.
5. `권장 마스터 프롬프트` 또는 `34회기에서 발견한 오류를 한 번에 반영할 때` 프롬프트로 두 번째 버전을 만든다.
6. 새 자료와 새 학생 표현의 홀드아웃 10회기 40턴을 실행한다.
7. 다른 교사나 성인 시험자가 가상 학생으로 4~6턴씩 대화하고 자연스러움, 학생 생각의 소유권, 근거, 종료를 채점한다.
8. 저작권, 개인정보, 모바일 화면을 확인한 뒤 학생에게 제공한다.

핵심은 긴 프롬프트나 자동평가 통과 자체가 아니다. 교사가 수업 자료의 경계, 학생에게 열어 둘 생각, 강제하지 않을 답, 실제로 쓰고 싶은 말투를 구체적으로 제공하고 완성된 HTML을 학생 사용 전에 직접 대화하며 검토하는 것이다. 합성 34회기는 오류를 찾는 프리파일럿이며 실제 학생의 자연스러움이나 학습 효과를 대신하지 않는다.
