# 평가 대시보드 시연 완성 계획서

작성 기준일: 2026-08-28

이 문서는 현재 구현된 평가 대시보드를 교사가 처음부터 끝까지 직접 시연할 수 있는
상태로 완성하기 위한 실행 계획이다. 각 단계는 독립적으로 작동하고 검증된 뒤 다음
단계로 넘어간다.

## 1. 시연의 최종 목표

교사 한 명이 다음 흐름을 한 번의 시연에서 막힘없이 수행한다.

```text
로그인
  → 평가 준비 프렙 작성
  → 성취기준·평가 목표·루브릭 확정
  → Notion 학생 결과물 읽어오기
  → AI 평가 초안 생성
  → 교사 검토·재채점·확정
  → 평가활동별 결과와 평가 포워드 확인
  → 성장 기록 보드(생기부)에서 누적 변화 확인
  → 학교 양식 PDF 업로드·항목 연결
  → 학교 양식에 맞춘 기록 미리보기·PDF 다운로드
```

시연의 성공은 화면이 존재하는지가 아니라 다음 조건으로 판단한다.

- 교사가 준비 단계와 다음 행동을 스스로 이해한다.
- Notion 원본 결과물을 실제로 읽어 평가 근거로 사용한다.
- AI 초안과 교사 확정 평가가 구분된다.
- 교사 수정 점수와 피드백이 모든 집계에 즉시 반영된다.
- 성장 기록과 세특 초안은 원결과물 근거를 추적할 수 있다.
- 학교 양식 PDF의 구조와 글자 수 조건이 최종 작성 결과에 반영된다.
- 비밀키, Notion 토큰, 학생 자료가 다른 교사나 공개 URL에 노출되지 않는다.

## 2. 시연 범위 결정

### 반드시 보여줄 기능 — P0

1. Google 또는 이메일 교사 로그인
2. 평가 준비 프렙 6단계 상태
3. 성취기준·평가 목표·루브릭 연결
4. Notion 데이터베이스 속성 또는 학생 페이지 본문 읽기
5. AI 평가 초안과 근거 표시
6. 교사 검토·점수 수정·최종 확정
7. 교사 확인 우선 학생 선별
8. 평가활동별 결과 및 학생별 누적 성장
9. 학교 양식 PDF 업로드와 항목 매핑
10. 학교 양식 기반 작성 결과 미리보기와 PDF 다운로드

### 시연 후 확장 — P1

- 스캔 PDF OCR 자동 인식
- Notion 결과물 수정본 증분 동기화
- 여러 학생 일괄 평가와 일괄 PDF 생성
- 교사별 Notion OAuth 연결
- 확정 보고서의 선택적 Notion 페이지 저장
- 학기·기간별 세특 일괄 편집

### 이번 시연에서 제외 — P2

- HWP/HWPX/Word/Excel 양식 직접 편집
- 평가 결과의 Notion 양방향 자동 동기화
- 교사 승인 없는 자동 최종 평가
- 학교 행정 시스템에 자동 제출
- 스캔 상태가 매우 나쁜 PDF의 완전 자동 복원

## 3. 현재 구현 상태

| 영역 | 현재 상태 | 시연 전 남은 일 |
| --- | --- | --- |
| 인증 | Supabase Auth와 Google 로그인 코드 존재 | 운영 Redirect URL과 실제 로그인 점검 |
| 대시보드 | 진행률, 남은 평가, 이어서 채점 구현 | 실데이터 연결 상태와 오류 안내 점검 |
| 평가 준비 프렙 | `/dashboard/prep` 및 6단계 배너 구현 | 프렙 입력값의 영구 저장·버전 확정 |
| 루브릭 | 생성·수정·기준 편집 구현 | 관찰 증거와 성취기준 연결을 더 명확히 표시 |
| Notion 읽기 | 속성 및 학생 페이지 본문 읽기 구현 | 연결 미리보기, 수정본 정책, 실데이터 검증 |
| AI 평가 | 댓글별 AI 초안 생성 코드 존재 | 배치 실행, 검토 사유, 확신도 표시 |
| 교사 평가 | 점수·근거·피드백 저장 구현 | 확정 상태와 수정 이력 저장 |
| 평가 결과 비교 | AI 초안과 교사 평가 비교 화면 존재 | 기준별 차이와 재채점 이유 표시 |
| 성장 기록 | 활동·학생별 집계 보드 구현 | 평가 포워드와 활동 간 변화 영구 저장 |
| 학교 PDF 양식 | 미구현 | 업로드·분석·매핑·작성·다운로드 전체 구현 |
| 내보내기 | 계획만 존재 | PDF 생성과 감사 기록 구현 |

### 확인된 Supabase 상태

- 핵심 테이블과 RLS는 생성되어 있다.
- 현재 운영 데이터에는 수업활동·학생 결과물·루브릭이 존재한다.
- 현재 운영 `evaluations`에는 코드가 사용하는 `source` 열이 없어
  `007_evaluation_sources.sql` 적용이 선행되어야 한다.
- 마이그레이션 이력이 기록되어 있지 않아 운영 DB와 저장소 SQL의 일치 검증이 필요하다.
- `SECURITY DEFINER` 함수의 공개 실행 권한과 일부 RLS 성능 경고를 시연 전 정리해야 한다.

## 4. 시연 데이터 세트

시연은 실제 학생 개인정보 대신 고정된 가상 데이터로 반복 가능하게 만든다.

### 최소 데이터

- 교사 계정 1개
- 평가활동 2개
- 학생 식별자 3개: `5-1-01`, `5-1-02`, `5-1-03`
- 학생별 결과물 2회분, 총 6개 이상
- 성취기준이 포함된 루브릭 1개
- 기준 3개, 기준당 0~5점
- AI와 교사의 점수가 다른 사례 1개
- 근거 부족으로 교사 검토가 필요한 사례 1개
- 이전 평가 포워드를 다음 결과물에서 반영한 사례 1개
- 개인정보가 없는 학교 양식 샘플 PDF 1개

### 데이터 재설정

- 시연용 데이터에는 `metadata.demo = true`를 기록한다.
- 시연 계정 소유 데이터만 초기화하는 별도 스크립트를 둔다.
- 운영 학생 데이터는 초기화 대상에 포함하지 않는다.
- 시연 전 한 번의 명령 또는 관리자 버튼으로 같은 시작 상태를 복원한다.

## 5. 단계별 개발 계획

## 단계 0 — 시연 기반 안정화

목적: 이후 기능을 만들기 전에 로컬·배포·Supabase 스키마를 같은 상태로 맞춘다.

### 구현 작업

- `007_evaluation_sources.sql`을 운영 Supabase에 적용한다.
- 저장소의 모든 마이그레이션과 운영 DB 열·제약·인덱스를 비교한다.
- 새 프로젝트 기본값과 무관하게 `authenticated` 역할의 필요한 권한을 명시한다.
- 모든 공개 테이블의 RLS 소유권 정책을 확인한다.
- `handle_new_user`, `rls_auto_enable` 등 공개 실행 가능한
  `SECURITY DEFINER` 함수의 `EXECUTE` 권한을 회수한다.
- 로컬 `.env.local` 또는 배포 환경변수 연결을 검증한다.
- Google 로그인 Site URL과 Redirect URL을 확인한다.
- 데모 데이터를 반복 생성할 fixture 또는 seed를 만든다.

### 완료 기준

- 로그인 후 `/dashboard`, `/dashboard/prep`, `/dashboard/growth`가 오류 없이 열린다.
- `teacher-manual`과 `ai-draft` 평가가 같은 결과물에 동시에 저장된다.
- 다른 교사 계정으로 시연 계정의 프로젝트·결과물·PDF를 읽지 못한다.
- Supabase Security Advisor의 고위험 경고가 없다.
- 시연 데이터를 두 번 초기화해도 중복·외래키 오류가 없다.

### 시연 관문

`로그인 → 대시보드 → 기존 수업활동 열기`까지 1분 안에 수행한다.

## 단계 1 — 평가 준비 프렙 영구 저장

목적: 현재 계산형 준비 상태를 실제 평가 준비 문서와 활성 버전으로 발전시킨다.

### 데이터

- `assessment_preps`
  - 소유 교사, 프로젝트, 평가 목표, 학년·교과, 상태, 현재 버전
- `assessment_prep_versions`
  - 성취기준, 평가 목표, 안전 규칙, 루브릭 버전의 불변 스냅샷
- 기존 `projects`와 `rubrics` 연결 유지

### 화면

- `/dashboard/prep`
  - 수업활동별 6단계 상태와 다음 행동
- `/dashboard/prep/[prepId]`
  - 수업 맥락
  - 성취기준과 평가 목표
  - Notion 결과물 위치
  - 루브릭 검토
  - 학생 안내
  - 샘플 시험 평가

### 구현 작업

- 현재 `lib/assessment-prep/readiness.ts`를 DB 저장형 상태와 연결한다.
- 단계별 저장은 Server Action에서 로그인 교사와 프로젝트 소유권을 다시 확인한다.
- `이 평가안 활성화` 시 버전 스냅샷을 생성한다.
- 이미 활성화된 버전은 수정하지 않고 새 버전을 만든다.
- 활성 평가안이 없는 프로젝트는 AI 평가 실행을 막고 다음 행동을 안내한다.

### 완료 기준

- 새로고침·로그아웃 후에도 준비 상태가 유지된다.
- 성취기준 원문, 평가 목표, 루브릭이 한 화면에서 연결되어 보인다.
- 과거 평가가 나중에 수정한 프렙의 영향을 받지 않는다.
- 다른 교사의 프렙을 조회·수정할 수 없다.

### 시연 관문

빈 수업활동에서 프렙을 작성하고 `6/6 준비 완료` 상태로 활성화한다.

## 단계 2 — Notion 결과물 읽기 완성

목적: 학생이 복제한 Notion 템플릿 결과물을 안전하게 평가 입력으로 가져온다.

### 구현 작업

- Notion 읽기 연결 상태를 프렙 단계에서 확인한다.
- 데이터베이스 URL과 다음 속성을 미리보기 한다.
  - 학생 식별자
  - 결과물 내용 속성 또는 페이지 본문
  - 활동명
  - 마지막 수정 시각
- 첫 3개 결과물을 저장 전 미리 보여준다.
- Notion 페이지 본문은 하위 블록과 페이지네이션을 포함해 읽는다.
- `notion_page_id + last_edited_time`을 기준으로 새 결과와 수정본을 구분한다.
- 이미 평가한 원문을 조용히 덮어쓰지 않는다.
- Notion 장애 시 이미 가져온 결과물과 평가는 그대로 유지한다.
- Notion은 읽기 권한만 사용하고 쓰기 실패 경로를 만들지 않는다.

### 화면 안내

- `연결됨`, `DB 미공유`, `속성 불일치`, `토큰 만료`, `새 결과 없음`을 구분한다.
- 가져온 결과물마다 원본 Notion 페이지 링크와 읽은 시각을 표시한다.
- 개인정보가 포함될 수 있음을 가져오기 전에 안내한다.

### 완료 기준

- 속성형 결과물과 페이지 본문형 결과물을 각각 3개 이상 가져온다.
- 같은 결과물을 다시 읽어도 불필요한 중복이 생기지 않는다.
- 수정된 결과물은 새 평가 근거 버전으로 표시된다.
- Notion 원본 페이지가 변경되지 않는다.

### 시연 관문

Notion 샘플 DB에서 학생 결과물 3개를 읽고 평가 목록에 즉시 표시한다.

## 단계 3 — AI 평가 초안과 자동 선별

목적: 교사가 모든 결과물을 처음부터 읽는 대신 AI 초안과 검토 우선순위를 받는다.

### 평가 출력 계약

- 기준별 점수
- 기준별 원문 근거 인용
- 판정 이유
- 전체 피드백
- 평가 포워드 초안
- 확신도
- 교사 검토 사유 배열

### 검토 사유

- 근거 부족
- 루브릭 기준 간 모순
- 점수 경계에 가까움
- 결과물이 너무 짧거나 손상됨
- 학생 식별자 누락
- AI 응답 형식 오류
- 기존 교사 평가와 큰 차이

### 구현 작업

- 활성 프렙 버전과 루브릭 버전을 AI 요청에 고정한다.
- 점수를 제안하기 전에 원문 증거를 찾도록 출력 스키마를 분리한다.
- 한 결과물 평가와 선택 결과물 일괄 평가를 지원한다.
- 일괄 실행은 개별 실패를 전체 실패로 만들지 않는다.
- AI 초안은 `source = ai-draft`로만 저장한다.
- 구조화 출력 검증 실패 시 저장하지 않고 재시도 가능한 상태로 둔다.
- 비용·모델·프롬프트 버전을 `raw_output` 또는 별도 감사 필드에 기록한다.

### 완료 기준

- 3개 결과물을 일괄 평가하고 각 결과에 근거가 표시된다.
- 근거 없는 점수는 교사 검토 대상으로 자동 표시된다.
- AI 초안이 교사 확정 평가나 성장 기록을 직접 바꾸지 않는다.
- 같은 입력과 버전의 중복 실행을 경고한다.

### 시연 관문

`AI 초안 만들기` 한 번으로 3명의 초안과 `교사 확인 우선` 목록을 생성한다.

## 단계 4 — 교사 검토·재채점·확정

목적: 교사가 가장 중요한 판단을 빠르게 확인하고 수정한 결과를 최종 기준으로 만든다.

### 화면

- 원결과물
- 평가 기준과 성취기준
- AI 점수·근거·피드백
- 교사 점수·근거·피드백 편집
- AI와 교사 차이
- 재채점 이유
- `교사 최종 확정` 버튼

### 데이터

- `evaluation_revisions` 또는 동등한 불변 수정 이력
- 평가 상태
  - `ai_draft`
  - `review_required`
  - `teacher_reviewed`
  - `teacher_confirmed`
- 확정 시각과 확정 교사

### 구현 작업

- 기준별 점수 변경 시 총점을 서버에서 다시 계산한다.
- AI 근거와 교사 근거를 덮어쓰지 않고 구분한다.
- 재채점 전후와 수정 이유를 기록한다.
- 교사 확정 평가만 통계·성장 기록·학교 양식 작성에 사용한다.
- 되돌리기는 과거 버전을 삭제하지 않고 새 revision을 만든다.

### 완료 기준

- AI 3점 결과를 교사가 4점으로 수정하면 모든 관련 화면에 4점이 반영된다.
- 누가 언제 어떤 이유로 수정했는지 확인할 수 있다.
- 미확정 AI 초안은 성장 기록 보드에 포함되지 않는다.

### 시연 관문

검토 우선 학생 한 명의 근거를 확인하고 점수·피드백을 수정해 최종 확정한다.

## 단계 5 — 평가활동 결과와 평가 포워드

목적: 댓글 하나의 채점을 학생 한 명의 활동 최종결과로 정리한다.

### 데이터

- `student_activity_results`
  - 학생 식별자
  - 최종 점수와 기준별 요약
  - 강점과 보완점
  - 평가 포워드
  - 원결과물·수정본·평가 근거 참조
  - 교사 확정 상태

### 화면

- `/dashboard/projects/[projectId]/results`
  - 제출·AI 평가·교사 확정 진행률
  - 검토 필요 필터
  - 학생별 최종결과
  - 기준별 학급 분포
  - 취약 기준
  - 좋은 근거 후보

### 완료 기준

- 학생별 결과가 원평가와 연결된다.
- 평가 포워드는 다음 활동에서 수행할 수 있는 구체적인 한 행동으로 작성된다.
- 교사가 수정한 평가 포워드가 보존된다.
- 미확정 결과는 보고서와 학교 양식 작성 대상에서 제외된다.

### 시연 관문

한 활동의 3명 평가를 확정하고 학급 취약 기준과 학생별 평가 포워드를 보여준다.

## 단계 6 — 성장 기록 보드(생기부) 완성

목적: 단순 평균이 아니라 이전 피드백을 다음 결과물에서 어떻게 반영했는지 보여준다.

### 데이터

- `student_growth_records`
  - 이전 활동과 다음 활동
  - 기준 키
  - 이전·현재 원문 근거
  - 변화 유형
  - 평가 포워드 반영 여부
  - 교사 확인 상태
- `student_term_summaries`
  - 기간
  - 포함 활동
  - 반복 강점·보완점
  - 세특 근거
  - AI 초안과 교사 확정 문장

### 구현 작업

- 같은 학생 식별자의 활동 결과를 시간순으로 연결한다.
- 기준명이 바뀌어도 비교할 수 있는 안정적인 criterion key를 사용한다.
- `향상`, `유지`, `지원 필요`, `관찰되지 않음`을 근거와 함께 표시한다.
- 성장 서사는 두 활동 이상의 근거가 있을 때만 생성한다.
- 세특 초안마다 사용한 평가·원문 근거 ID를 보존한다.

### 완료 기준

- 같은 학생의 두 활동이 타임라인에 나타난다.
- 이전 평가 포워드와 다음 결과물의 반영 문장을 나란히 확인한다.
- 근거가 한 번뿐인 특성을 반복적 성장으로 표현하지 않는다.
- 교사가 확정하지 않은 세특 문장은 내보낼 수 없다.

### 시연 관문

학생 한 명의 두 활동을 열어 `이전 피드백 → 다음 결과물 변화 → 세특 근거`를 보여준다.

## 단계 7 — 학교 양식 PDF 작성 도우미

목적: 학교별 문서 양식을 한 종류의 입력인 PDF로 통일하고, 확정 평가를 그 양식에 맞춰 작성한다.

### 1차 시연 지원 범위

- 텍스트가 포함된 PDF
- AcroForm 입력 필드가 있는 PDF
- 일반 PDF에서 교사가 직접 지정한 텍스트 영역
- 한글 문서용 글꼴 포함
- 한 학생 결과 미리보기와 PDF 다운로드

스캔 PDF OCR은 P1으로 둔다. 1차 시연에서는 텍스트 추출이 가능한 개인정보 없는
학교 양식 PDF를 사용한다.

### 저장 구조

- Supabase Storage 비공개 버킷: `school-form-templates`
- 경로: `{owner_id}/{template_id}/original.pdf`
- `school_pdf_templates`
  - 소유 교사
  - 학교·문서 유형·학년도
  - 파일 경로, SHA-256, 페이지 수
  - 분석 상태와 오류
  - 원본 버전
- `school_pdf_template_fields`
  - 페이지 번호
  - 항목명
  - 좌표와 크기
  - 데이터 소스 키
  - 글자 수·줄 수·글꼴 크기
  - 필수 여부

### PDF 데이터 소스 키

- `student_key`
- `project_title`
- `assessment_period`
- `achievement_standards`
- `learning_goal`
- `criterion_results`
- `strengths`
- `growth_needs`
- `feedback_forward`
- `growth_summary`
- `special_record_draft`
- `teacher_final_text`

### 구현 작업

1. PDF 업로드
   - MIME `application/pdf`만 허용
   - 파일 크기와 페이지 수 제한
   - 비공개 버킷과 교사별 폴더 RLS
2. PDF 분석
   - AcroForm 필드 추출
   - 텍스트·표·항목명·좌표 추출
   - 자동으로 추정한 항목은 확정 전 상태로 표시
3. 항목 매핑
   - 교사가 각 PDF 칸을 평가 데이터 키에 연결
   - 글자 수, 문체, 문장 종결 형식 설정
4. 작성
   - 교사 확정 평가만 사용
   - 값이 없는 필수 칸은 생성 대신 `확인 필요`로 표시
   - 학교 글자 수에 맞게 축약하되 근거를 새로 만들지 않음
5. 미리보기와 출력
   - 원본 PDF 위에 작성 결과를 렌더링
   - 페이지 잘림·겹침 경고
   - 교사 확정 후 다운로드

### 권장 라이브러리 검토

- 입력 필드·페이지 분석 및 작성: `pdf-lib` + `@pdf-lib/fontkit`
- AcroForm 채우기와 PDF 생성: `pdf-lib`
- 서버 처리만 허용하고 브라우저 번들에는 원본 PDF 처리 코드를 최소화한다.
- 실제 채택 전 한글 글꼴 임베딩과 Next.js 서버 런타임 호환을 작은 실험으로 검증한다.

### 보안

- Storage 버킷은 비공개로 만든다.
- 업로드·조회·삭제는 `{owner_id}` 폴더와 로그인 사용자 ID가 같은 경우만 허용한다.
- 미리보기 URL은 짧은 만료 시간의 signed URL 또는 인증 다운로드를 사용한다.
- 학교 양식 원본과 완성 PDF는 공개 URL을 만들지 않는다.
- 파일 이름에 학생 실명이나 학번을 넣지 않는다.

### 완료 기준

- 학교 양식 PDF 한 개를 업로드하고 다시 열 수 있다.
- 자동 추출 또는 수동 지정한 칸 5개 이상을 데이터에 연결한다.
- 교사 확정 평가로 한 학생의 완성 PDF를 만든다.
- 긴 문장은 영역 밖으로 넘치지 않고 경고 또는 축약된다.
- 다른 교사는 원본·미리보기·완성 PDF를 다운로드할 수 없다.
- 출력 PDF를 이미지로 렌더링해 한글 깨짐, 겹침, 잘림이 없다.

### 시연 관문

학교 양식 PDF를 업로드하고 학생 한 명을 선택해 5개 항목을 자동 작성한 뒤 PDF를 내려받는다.

## 단계 8 — 내보내기와 감사 기록

목적: 무엇을 어떤 평가 버전으로 내보냈는지 추적한다.

### 데이터

- `assessment_exports`
  - 범위, 형식, 평가·프렙·학교 양식 버전
  - 콘텐츠 해시
  - 상태와 오류
  - 파일 이름과 Storage 경로
  - 생성·완료 시각

### 구현 작업

- 같은 버전을 다시 출력할 때 중복 경고를 표시한다.
- 실패한 PDF 생성이 평가 원본을 변경하지 않게 한다.
- 완성 PDF 보관과 즉시 다운로드 중 교사가 선택할 수 있게 한다.
- Notion 페이지 저장은 별도 선택 기능이며 기본 시연 경로에서 제외한다.

### 완료 기준

- 누가 언제 어떤 버전으로 PDF를 생성했는지 확인한다.
- PDF 생성 실패 후 재시도할 수 있다.
- 과거 내보내기와 현재 평가의 차이를 표시한다.

### 시연 관문

작성 결과를 확정하고 다운로드 이력에서 같은 파일을 다시 확인한다.

## 단계 9 — 통합 검증과 시연 리허설

목적: 기능별 성공을 하나의 교사 경험으로 연결한다.

### 자동 검증

- TypeScript 검사
- ESLint
- Next.js 프로덕션 빌드
- 프렙 readiness 단위 테스트
- Notion 속성·페이지 본문 파서 테스트
- AI 구조화 출력 검증 테스트
- 교사 재채점 총점 재계산 테스트
- 성장 기록 근거 연결 테스트
- PDF 필드 매핑·글자 수·페이지 렌더링 테스트
- RLS 허용·차단 테스트

### 브라우저 검증

1. 로그인
2. 프렙 생성·활성화
3. Notion 결과 3개 읽기
4. AI 초안 일괄 생성
5. 검토 우선 학생 재채점·확정
6. 활동 결과와 평가 포워드 확인
7. 성장 기록 확인
8. 학교 PDF 업로드·매핑
9. 학생 선택·미리보기·다운로드

### 실패 상황 리허설

- Notion 토큰 오류
- Notion DB 미공유
- AI API 키 없음 또는 일시 실패
- PDF가 스캔 이미지뿐인 경우
- 필수 PDF 칸에 연결할 데이터가 없는 경우
- Supabase 권한 오류
- 네트워크 중단 후 재시도

### 시연 완료 기준

- 전체 시나리오를 10~15분 안에 완료한다.
- 새로고침 후에도 진행 상태와 확정 평가가 유지된다.
- 어떤 실패도 평가 원본 삭제나 확정 상태 손상으로 이어지지 않는다.
- 시연자가 별도 개발자 설명 없이 다음 버튼을 찾을 수 있다.
- 같은 시연을 세 번 반복해 동일한 결과가 나온다.

## 6. 권장 개발 순서와 중단 규칙

| 순서 | 개발 묶음 | 다음 단계로 넘어가는 조건 |
| --- | --- | --- |
| 0 | Supabase·인증·데모 데이터 안정화 | 핵심 3개 화면과 source 분리 정상 |
| 1 | 프렙 영구 저장 | 활성 프렙 버전 생성·재조회 성공 |
| 2 | Notion 결과물 읽기 | 3개 결과물 미리보기·저장·중복 방지 |
| 3 | AI 초안·자동 선별 | 근거와 검토 사유가 있는 초안 3건 |
| 4 | 교사 재채점·확정 | 수정 이력과 최종 점수 재집계 |
| 5 | 활동 결과·평가 포워드 | 학생 3명 최종결과 확정 |
| 6 | 성장 기록 | 한 학생의 두 활동 변화 근거 확인 |
| 7 | 학교 PDF 작성 도우미 | 5개 칸 매핑·한글 PDF 다운로드 |
| 8 | 내보내기 이력 | 버전·해시·재시도 확인 |
| 9 | 통합 리허설 | 전체 시나리오 3회 성공 |

한 단계의 완료 기준이 충족되지 않으면 다음 단계의 기능을 본격 구현하지 않는다.
특히 PDF 기능을 먼저 만들기 전에 교사 확정 평가와 성장 기록의 데이터 계약을 고정해야 한다.

## 8. 첫 번째 개발 묶음

1. 운영 DB에 `007_evaluation_sources.sql` 적용
2. 로컬 또는 배포 환경의 Supabase 연결 검증
3. 시연용 가상 데이터 seed
