# 교사 지문 분석 기반 RAG 반응식 질문 챗봇 설계 · 2026-09-05

「챗봇 스크립트 개선안」(`docs/챗봇-스크립트-개선안.md`)이 지금 있는 스크립트를 고치는 문서라면, 이 문서는 **다음 판의 구조**다. 교사가 지문을 넣으면 챗봇이 그 지문을 분석해 지식 단위로 쪼개 색인하고, 수업 중에는 **학생의 말과 대화 상태에 반응해** 필요한 근거만 꺼내 답하는 구조를 그린다.

## 1. 왜 RAG인가 — 지금 실패의 뿌리

개선안 2절의 실패 여섯 가지는 규칙을 한 줄씩 더해 막을 수 있지만, 뿌리는 하나다. **검색이 낱말 겹침뿐이다.**

| 실패 | 뿌리 |
| --- | --- |
| `왜 그렇게 됐어요?` → "없어요" | "그렇게"가 무엇을 가리키는지 모른 채 낱말만 찾았다. 대화 상태가 검색에 들어가지 않는다 |
| `잔반` → 본문의 `남은 음식`을 못 찾음 | 표면 낱말이 다르면 못 찾는다. 의미 검색이 없다 |
| `42%` → "없어요" | 제목 청크를 통째로 버렸다. 청크에 **역할 표시**가 없어 "근거로는 안 쓰되 사실로는 쓴다"를 못 한다 |
| 같은 질문 반복 | 검색 결과에 "이미 보여 준 것"이 반영되지 않는다 |
| `다른 학교도…`에 엉뚱한 문장 | 질문 의도(전이)가 검색 전략을 바꾸지 않는다 |

규칙을 더 쌓는 대신 **분석 → 색인 → 반응식 검색 → 근거 제한 생성 → 검증**의 다섯 단계로 나누면, 각 실패가 어느 단계의 문제인지 보이고 그 단계만 고치면 된다.

## 2. 저장소에 이미 있는 것 — 새로 짓지 않는다

| 있는 것 | 어디 | RAG에서의 자리 |
| --- | --- | --- |
| 카드 8종(`vocabulary`·`fact`·`inference`·`background`·`research`·`expected_question`·`extension`·`dialogue_design`), `source_type`·`source_text`·`source_location`·`confidence`·`knowledge_status` | `docs/THINKING_CARD_KNOWLEDGE_BASE.md`, `lib/questioning-cards.ts`, 마이그레이션 004 | **지식 단위(청크)의 스키마.** 그대로 쓴다 |
| Teacher AI / Student AI 분리 | 같은 문서 1절 | 분석은 수업 전 고성능 모델, 수업 중은 Flash급 |
| `findRelevantCards()` — 낱말·의도·상태 보너스, 문턱 4점, 상위 4장 | `lib/questioning-card-store.ts` | 어휘 검색 갈래. 여기에 의미 검색을 **더한다** |
| `buildMaterialReasoningContext()` — 질문과 겹치는 문장 ±1 창 | `lib/gemini/questioning-board.ts` | 문장 청크 검색 갈래. 카드 검색과 **융합**한다 |
| `embedding_json`·`embedding_model` 열 | 마이그레이션 004 | 비어 있다. **임베딩을 계산하는 코드가 한 줄도 없다** |
| 005 pgvector (미적용) | `supabase/migrations/005` | 카드 수천 장 넘을 때만 |
| 대화 정책 — 학생 상태 6종, 허용 동작, 질문 허용 여부 | `lib/questioning-dialogue-policy.ts` | **검색 전략을 고르는 입력**이 된다 (지금은 생성만 제어) |
| 2국면·B1/B2·난이도·신호 채점 | `lib/questioning-conversation-phase.ts`, `lib/questioning-target-signals.ts` | 생성 뒤 후처리. 그대로 두되 2국면 질문의 재료를 검색에서 받는다 |
| 미답변 질문 → 교사 답 카드, 리서치 카드 | `addTeacherAnswerCard`, `addLiveResearchCard` | 학습 루프. 그대로 |
| 회귀 평가 49회기 | `scripts/run-questioning-dialogue-eval.mjs` | 검색 정확도 지표를 더한다 |

즉 **부품은 다 있고 두 가지가 없다.** ① 의미 검색(임베딩) ② 대화 상태가 검색을 바꾸는 "반응" 층.

## 3. 다섯 단계

```text
[수업 전]  교사 지문 ──▶ A. 분석 ──▶ B. 색인
[수업 중]  학생 말 + 대화 상태 ──▶ C. 반응식 검색 ──▶ D. 근거 제한 생성 ──▶ E. 검증·국면 ──▶ 학생
                                          ▲                                        │
                                          └──── 미답변·교사 답·리서치 카드 (학습 루프) ◀┘
```

### A. 분석 (Teacher AI, 수업 전 한 번)

교사가 지문을 붙여 넣으면(또는 이미지를 올리면 `analyze-image`) 다음을 만든다. 대부분 `buildLocalCardSet()`이 이미 하고, 굵은 것만 새로 더한다.

1. **문장 청크** — 문단 번호·문장 번호를 붙여 자른다. `sentencesOf()`와 같되 결과를 카드(`fact`, `source_type: passage`, `source_location: "2문단 3문장"`)로 **저장**한다. 지금은 매 요청마다 다시 자른다.
2. **제목 청크에 `role: title`** — 근거 인용에서는 빼고 사실 검색에서는 쓴다. "42%"는 여기서 나온다.
3. 어휘 카드 — 사전 뜻·문맥 뜻·쓰인 문장. **표면형이 다른 표현(`잔반`↔`남은 음식`)을 `aliases`로** 함께 적게 한다. 임베딩이 없을 때의 보험이다.
4. 추론 카드 — `reasoning_type: cause_effect`에 **원인 문장과 결과 문장의 청크 번호**를 잇는다. "왜"는 이 간선을 탄다.
5. 예상 질문 카드 — 6렌즈(`literal`·`vocabulary`·`causal`·`skeptical`·`personal`·`boundary`)로 12개. `relatedQuestions`에 붙인다(이미 있음).
6. **한계 카드** — 지문이 단정하지 않은 것(`메뉴가 달랐고 날씨도 같지 않아`), 다루지 않은 것. 전이·가설 질문의 근거가 된다. 지금 `misconceptionWatch`·`openQuestions`가 비슷하나 카드로 저장되지 않는다.
7. 성취기준 표적(`buildStandardTargets`)마다 **표적 카드 1~2장** — 2국면에서 "이 문장을 먼저 다시 보고"에 쓸 문장을 미리 골라 둔다.

교사 검토 화면은 지금 보드의 카드 목록을 그대로 쓴다. `needs_review`는 학생 답에 안 쓴다는 규칙도 그대로다.

### B. 색인 (하이브리드)

| 갈래 | 방법 | 비고 |
| --- | --- | --- |
| 어휘 | 조사 제거 + 활용형 변형(`termVariants`) + `aliases` | 있음. codex 브랜치의 `termVariants`를 서버 쪽으로도 옮긴다 |
| 의미 | `gemini-embedding-001`(768차원)로 카드 `content + source_text + relatedQuestions`를 임베딩 → `embedding_json` | **새로 만든다.** 지문당 카드 30~60장이라 앱 안 코사인으로 충분. 5천 장 넘을 때 005 |

임베딩은 교사 키로 수업 전 한 번만 계산한다. 학생 발화 임베딩은 수업 중 턴마다 한 번(768차원 한 벡터, 비용 무시할 수준)이며 **개인정보를 가린 뒤**(codex 브랜치 `redactPersonalInformation`) 보낸다. 키가 없으면 어휘 갈래만으로 돌아간다 — 지금과 같다.

### C. 반응식 검색 — 학생 상태가 검색을 바꾼다

질의는 학생 발화 하나가 아니다. `대화 정책`이 판정한 상태와 직전 근거가 함께 들어간다.

| 학생 상태 / 발화 유형 | 검색 전략 | 꺼내는 것 |
| --- | --- | --- |
| 지시어 질문 (`왜 그렇게 됐어요?`, `그건 왜요?`) | 질의를 **직전 근거 문장 + 발화**로 확장 | 직전 청크의 `cause_effect` 간선 → 원인 청크, 이웃 ±1 |
| 어휘 1단계 (`X가 뭐예요?`) | 어휘 카드 정확 일치 → `aliases` | 사전 뜻만 |
| 어휘 2단계 (`이 글에서는?`) | `lastTerm`의 어휘 카드 `contextSentence`; 없으면 `aliases`·임베딩으로 본문 청크 | 쓰인 문장 + 문맥 뜻 |
| 사실·수치 (`몇`, `얼마나`, 숫자) | **숫자 정확 일치를 최우선**, 제목 청크 포함 | 그 숫자가 든 청크 |
| 전이·일반화 (`다른 학교도…`) | 한계 카드 우선 | 조건 문장 |
| 원인 가설 (`…때문에 …거죠?`) | `cause_effect` 카드에서 지문이 **단정한** 원인이 있는지 | 있으면 그것, 없으면 한계 카드 |
| 요약·주장 | 첫·끝 청크 + `inference` 상위 | — |
| 반복 질문 | 직전 턴에 보여 준 청크 ID를 **제외** | 다른 근거 또는 "아까 그 문장" 안내 |
| 막힘 (`몰라요`) | 검색 안 함 | 첫 청크 하나 (지금과 같음) |
| 관계 회복·종료·딴소리·안전 | 검색 안 함 | 정책 문구 |
| 2국면 질문 차례 | 표적 카드 / 이해 확인용 청크 | 국면기가 붙일 질문의 재료 |

점수는 **RRF(순위 역수 융합)**로 어휘·의미 두 순위를 합치고, 기존 보너스(`knowledge_status`, `source_type: teacher +3`, 의도-유형, 학년)를 더한다. 문턱은 그대로 두되 융합 뒤 값으로 다시 잡는다. 결과는 카드 최대 4장 + 근거 청크 최대 5문장(±1 창 포함).

검색 결과는 턴마다 `retrieval_log`(질문, 상태, 뽑힌 ID와 점수, 생성이 실제 인용한 ID)로 남긴다. 이것이 5절의 평가 재료다.

### D. 근거 제한 생성

모델에게 **지문 전문을 주지 않는다.** 검색된 청크와 카드만 준다. 지금 Gemini 지시문은 전문 + 8문장 창을 모두 실어 모델이 창 밖에서 인용하는 길이 열려 있다.

구조화 출력(이미 `requestGeminiJson`을 쓴다)에 두 필드를 더한다.

```json
{
  "studentReply": "…",
  "evidenceIds": ["s-2-3", "card-17"],
  "sourceStatus": "supported | source_insufficient | out_of_scope",
  "primaryMove": "…"
}
```

지시문 핵심 세 줄:

- 답의 모든 사실은 `evidenceIds`의 청크 안에 있어야 한다. 청크에 없으면 `source_insufficient`로 두고 "이 글에는 나오지 않아요"라고 말한다.
- 인용은 청크 문장을 **그대로**(숫자·주체·시점 보존) 감싸서 쓴다.
- 제목 청크(`role: title`)는 사실로 쓰되 "제목에 …라고 나와요"로 말한다.

로컬 엔진(키 없음)도 **같은 검색 결과**를 받아 템플릿에 넣는다. 그러면 로컬과 Gemini가 같은 근거를 쓰고, 대체로 넘어가도 답이 튀지 않는다.

### E. 검증과 국면

생성 뒤, 국면 처리(`applyQuestioningConversationPhase`) 앞에 검증기를 둔다.

| 검사 | 실패하면 |
| --- | --- |
| `studentReply`의 따옴표 인용이 `evidenceIds` 청크 안에 실제로 있는가 (공백·문장부호 제거 후 포함) | 인용을 청크 원문으로 교체, 못 맞추면 로컬 답으로 |
| 숫자 보존 (`sameNumbers`) | 로컬 답으로 |
| 물음표 ≤ 1, 회복 턴이면 0 | 뒤 물음표를 마침표로 (지금 있음) |
| 개인정보 재호명 없음 | 가린 문구로 |
| `sourceStatus: supported`인데 `evidenceIds`가 비었음 | `source_insufficient`로 강등 |

검증 실패는 `retrieval_log`에 남긴다. 어떤 검색이 어떤 생성 실패를 낳는지 보이면 A·B·C 중 어디를 고칠지 안다.

## 4. 단일 HTML판 — 서버 없이 같은 구조

연수용 단일 HTML도 같은 다섯 단계를 **브라우저 안에서** 돈다. 규모가 작아 가능하다.

- **A·B(수업 전)**: [학생 화면 시작]을 누를 때 지문을 문장 청크로 자르고 어휘 색인을 만든다. 키가 있으면 Gemini 임베딩을 청크마다 한 번 계산해 `localStorage`에 지문 해시와 함께 저장한다(30문장 → 30회 호출, 수업 전 한 번). 교사 낱말 뜻 칸은 `낱말: 뜻 | 본문 표현`으로 `aliases`를 받는다.
- **C**: 3절 표를 그대로 옮긴다. 대화 상태는 이미 `lastTerm`·`lastEvidence`로 반쯤 있다 — 여기에 국면·직전 청크 ID·의도를 더한 상태 객체 하나로 모은다.
- **D**: `systemInstruction`에 지문 전문 대신 **검색된 청크 5개 + 카드**만 싣는다. 토큰이 줄어 무료 키 한도에도 유리하다. 로컬 엔진은 같은 청크를 템플릿에 넣는다.
- **E**: 인용 포함 검사·숫자 보존·물음표 수 — 세 함수를 그대로 옮긴다.

이렇게 하면 개선안 P0의 규칙 여섯 줄이 **검색 전략 표 여섯 줄**로 바뀐다. 규칙은 늘어날수록 서로 부딪히지만, 전략 표는 줄이 늘어도 독립적이다.

## 5. 평가 — 생성이 아니라 검색을 잰다

지금 회귀 평가는 응답의 형태(빈 답, 물음표 수, 종료 일관성…)를 본다. 여기에 **검색 정확도**를 더한다.

- 회귀 세트 49회기 207턴마다 **기대 근거 청크 ID**를 붙인다(한 번 손으로 단다. 기사 15개 × 문장 10여 개).
- 지표: `Recall@4`(기대 청크가 상위 4에 있는가), `인용 정확도`(생성이 인용한 문장이 기대 청크인가), `무근거율`(`supported`인데 인용 검증 실패).
- 목표: Recall@4 ≥ 0.9, 무근거율 0. 어휘 갈래만으로 먼저 재고, 임베딩을 켠 뒤 다시 재서 **의미 검색이 실제로 몇 턴을 살리는지** 숫자로 본다. 그 숫자가 작으면 임베딩은 안 켜도 된다.

## 6. 데이터 변경 — 최소

| 무엇 | 어떻게 |
| --- | --- |
| 문장 청크 저장 | 새 표 없음. `questioning_thinking_cards`에 `card_type: fact`, `source_type: passage`, `source_location`로. `metadata`에 `{ role: "title" \| "body", paragraph, sentence }` |
| 어휘 `aliases`, 인과 간선 | `metadata` jsonb. 열 추가 없음 |
| 임베딩 | 004의 `embedding_json`·`embedding_model` 그대로 |
| 검색 로그 | 새 표 `questioning_retrieval_logs`(lesson_code, student_id, turn, retrieved jsonb, cited jsonb, checks jsonb). 학생 발화 원문은 **가린 뒤** 저장. 선택 — 없으면 서버 로그로 |

| 3 | 근거 제한 생성 + 검증기 | `lib/gemini/questioning-board.ts`, 새 `lib/questioning-verify.ts` | 하루 |
| 4 | 회귀 세트에 기대 청크 달기 + Recall 지표 | `evals/…/sessions.json`, `scripts/run-questioning-dialogue-eval.mjs` | 반나절 |
| 5 | 임베딩 계산·저장·융합 | `lib/gemini/embeddings.ts`(새), 검색 함수 | 반나절 |
| 6 | 단일 HTML판 이식 | `webapp/질문챗봇-단일HTML.html`, 프롬프트 문서 | 하루 |

2까지 하면 개선안의 실패 여섯 가지가 구조적으로 사라지고, 4에서 그것을 숫자로 확인한다. 5는 4의 숫자를 보고 결정한다.

## 8. 조심할 것

- **학생 발화를 임베딩 API에 보내는 것**은 외부 전송이다. `QUESTIONING_STUDENT_LLM_ENABLED` 스위치 아래에만 두고, 가린 뒤 보낸다. 꺼져 있으면 어휘 갈래만 — 지금과 같은 경계다.
- 지문 전문을 카드로 저장하는 것은 교사가 붙여 넣은 자료에 한한다. 교과서·유료 기사는 지금처럼 `교과서를 살펴보세요` 경로(요약·위치만)로 간다. 청크 저장도 요약 문장까지만.
- 임베딩 모델을 바꾸면 전부 다시 계산해야 한다. `embedding_model` 열이 그래서 있다. 모델명이 다른 카드는 검색에서 어휘 갈래로만 쓴다.
- 무료 키는 분당 한도가 낮다. 수업 전 임베딩 계산은 교사 키로 천천히(초당 1회), 수업 중 학생 턴은 임베딩 실패 시 어휘 갈래로 조용히 넘어간다.
